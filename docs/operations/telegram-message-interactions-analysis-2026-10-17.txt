텔레그램 메시지 포커스 메뉴·반응·스와이프 분석
2026-10-17 / 앱 코드 변경 없이 분석 및 DavaQ 적용 규칙 정리

핵심
질문한 UX는 단순히 길게 눌렀을 때 액션 목록을 여는 기능보다 범위가 크다.
메시지 자체를 포커스 레이어에 유지하는 표현, 상황별 액션 권한, 반응 상태,
터치 시작 대상과 방향을 판정하는 제스처 조정, 다중 선택 모드가 함께 필요하다.

근거와 범위
- REA6.5.0으로 공식 Telegram Web A의 MessageContextMenu, ContextMenuContainer,
  ReactionSelector 3파일을 추가 분석했다. 파싱3개 성공/실패0. 선택 범위가 좁아
  그래프 커버리지는 partial이며, findings232는 버그232개라는 뜻이 아니다.
  소스 commit: f67a40879a7d78c2683ec5a296cf55bc22417d56.
- iOS 공개 소스는 commit f1dd7a2dbd02cbbf513e75d5695d8d36d1cf5838의
  ChatMessageBubbleItemNode, ChatSwipeToReplyRecognizer, ChatControllerOpenMessageContextMenu,
  ChatMessageContextControllerContentSource, NavigationContainer,
  InteractiveTransitionGestureRecognizer를 직접 읽었다.
- iOS Swift를 REA로 디컴파일한 것은 아니다. Web A의 REA 정적 분석과 iOS 소스 검토를
  구분한다. 이번에는 설치된 Telegram 모바일 앱의 실제 터치/영상 검증을 하지 않았다.
- Telegram은 플랫폼/버전에 따라 메뉴 진입 방식과 표현이 다르다. 질문한 포커스 장면은
  iOS형 UX를 중심으로 정의한다. 과거 공식 안내에도 Android 탭/iOS 길게 누르기 차이가 있다.

1. 길게 누르기: 원래 메시지를 중심에 둔 메뉴
확인한 iOS 구현:
- 메시지의 context source를 extracted content로 전달한다.
- 해당 소스는 blurBackground=true이며 takeView/putBack 경로를 제공한다.
- 메뉴를 열 때 선택된 메시지 콘텐츠와 원래 화면 위치를 찾아 전환한다.
- 메시지가 사라지면 메뉴도 닫히도록 메시지 존재 여부를 구독한다.
- 반응 아이템·현재 선택 반응·메시지 액션은 별도로 구성된다.
즉, 메시지 요약을 메뉴에 적는 것과 실제 메시지가 떠 보이는 포커스는 다른 구현이다.

DavaQ 현재:
- MessengerSheet가 휴대전화에서 하단에 뜨고 메시지는2줄 요약으로만 나온다.
- 원래 말풍선의 화면좌표/크기 측정 및 포커스 레이어 이동 경로는 없다.
- MessageBubble의 바깥 행 Pressable이 길게 누르기를 처리한다. 사진/파일에도
  별도의 길게 누르기가 있어 제스처 소유권을 일관되게 정리할 필요가 있다.

적용할 UX:
- 누른 버블의 좌표·크기·내용을 기준으로 포커스 미리보기, 주변 dim/blur,
  위쪽 반응 막대, 인접한 액션 메뉴를 배치한다.
- 화면 상하단/키보드/긴 메시지/사진/앨범에서는 사용 가능한 영역에 맞춰 위치를 조정한다.
- 원래 행의 높이는 유지한다. 메뉴 닫기 후 화면 위치와 키보드·입력 초안을 보존한다.
- 바깥 탭/뒤로가기는 메뉴만 닫는다. 해당 메시지가 삭제되거나 방이 바뀌면 닫는다.
- 미리보기 때문에 미디어 요청·통화·읽음 부작용이 중복 실행되지 않도록 표현을 분리한다.

2. 액션은 항상 같은 목록이 아니다
공개 Telegram 메뉴에는 canReply/canCopy/canPin/canForward/canReport/canSelect 등
가능 여부에 따른 구성이 있다. 보낸 사람, 메시지 종류, 방 권한, 보호된 콘텐츠에 따라 다르다.
권장 DavaQ 목록: 답장 / 복사 / 고정·해제 / 전달 / 신고 / 삭제 / 선택.
- 상대 메시지 편집은 노출하지 않는다. 삭제 범위는 나에게만/모두에게를 구분하고
  서버가 실제 허용하는 범위를 따른다. 상대 메시지 모두에게 삭제를 무조건 제공하지 않는다.
- 텍스트 복사와 사진/파일 저장은 다른 액션이다. 신고는 사유 선택 화면으로 이어진다.
- '선택'은 텍스트 부분 선택과 다중 메시지 선택을 구분해야 한다.
DavaQ 현재의 선택은 selectedMessageId 하나를 강조할 뿐, 선택 집합·선택 개수·일괄
전달/삭제 툴바가 없다. Telegram형 선택 모드로 보려면 이 부분을 별도로 구현해야 한다.

3. 반응은 스티커를 하나 덧붙이는 것보다 상태 모델이 중요하다
DavaQ의 기존 sticker API는 메시지+사용자 유일 키에 code를 upsert한다.
사용자당1개 반응을 변경하는 기반은 있으나 같은 반응을 다시 눌러 제거하는 경로는
확인한 POST API에 없다. 현재 버블 표시는 작은 스티커 배지 형태다.
적용 목표:
- 빠른 반응 막대, 전체 반응 선택기, 내가 선택한 반응 강조.
- 같은 반응 재선택 시 취소, 다른 반응 선택 시 교체, 반응별 수/참여자 표시.
- 이 낙관적 표시의 중복 탭·실패 롤백·멀티기기 변경을 검증한다.
- 빠른 더블 탭 반응은 선택 기능으로 두고, 싱글 탭·링크·사진 열기와 우선순위를 정한다.
Telegram의 여러 반응/유료 반응 정책까지 그대로 요구하는 것이 아니라 목표 기능의
범위에 맞는 반응 의미를 먼저 확정해야 한다.

4. 메시지 스와이프와 빈 배경 스와이프: 대상+방향+상태로 판정
확인한 iOS 소스:
- ChatSwipeToReplyRecognizer는1손가락이며 수평 우세와 수직 우세를 분리한다.
- Bubble 노드에서 allowBothDirections=false로 설정한다. 이 경로에서는 오른쪽
  이동을 거절하고 왼쪽 스와이프를 답장으로 쓴다.
- 확인한 커밋의 답장 실행 기준은 받은 메시지45pt, 보낸 메시지60pt이며 완료 시
  reply를 설정한다. 선택 모드 등에서는 시작을 막고, 진행 피드백·원복 애니메이션이 있다.
- 내비게이션은 스택에 이전 화면이 있을 때 .right를 허용한다. .right는 edge와
  center를 포함하므로 가장자리에서만 뒤로 갈 수 있는 구현이 아니다.
- 최초 터치를 hitTest해 하위 뷰/상위 뷰의 가로 제스처 소유 여부를 확인한다.
  중첩 컨트롤이 가로 제스처를 소유하면 가운데 내비게이션을 제한하거나 전부 거절한다.
따라서 '메시지냐 배경이냐'만으로 나누는 것보다 터치 대상과 방향·컨트롤의 소유권을
같이 구분해야 한다. 모든 말풍선 바깥 픽셀이 항상 동일 동작이라고 단정하지 않는다.

DavaQ 현재:
- SwipeToReply가 메시지 버블을 포함한 전체 행을 감싸고 있다.
- 오른쪽 이동12에서 인식, 수직10 초과 시 실패, 오른쪽56에서 답장 준비, 최대84 이동.
- 바깥 행이 실제 말풍선보다 넓어 빈 여백도 답장 제스처에 포함될 가능성이 있다.
  이는 코드상 위험이며 이번 실기기에서 재현한 결함으로 단정하지 않는다.
- Android/좁은 웹의 edge-back은 x0<=24인 경우 오른쪽으로 이동하면 부모가 capture한다.
- 답장도 오른쪽, 뒤로가기도 오른쪽이므로 방향 충돌 가능성이 있다.
- iOS는 이 custom edge-back 대신 기존 네이티브 내비게이션을 사용한다.

권장 입력 규칙(DavaQ 제품 사양)
터치 시작 대상               제스처                 결과
메시지/사진 콘텐츠           길게 누르기            해당 메시지 포커스 메뉴

빈 배경                     오른쪽 수평 스와이프    이전 화면으로 대화형 이동(이전 화면 있을 때)
사진 앨범/음성 재생바 등      가로 조작              해당 컨트롤 우선

중요한 구현 규칙:
- touch-down 시 대상 영역을 기록한다. 손가락이 이동해 말풍선을 지나가도 대상을 바꾸지 않는다.
- 버블의 실제 콘텐츠 영역과 행 전체의 빈 영역을 구분한다. 외부 여백을 자동으로 답장
  영역으로 쓰지 않는다. 사용성을 위해 확장할 hit slop은 명시적으로 정한다.
- OS 뒤로가기 영역은 존중하고, 앱 내부 네비게이션과 별개 답장이 동시에 실행되지 않는다.
- 세로 스크롤이 시작되면 long press/답장 준비를 취소한다. 답장이 확정되면 내비게이션 취소.
- 메뉴 또는 다중 선택 중에는 일반 모드의 답장/뒤로가기 제스처를 그대로 실행하지 않는다.
- 링크·버튼·재생바·앨범·텍스트 선택 핸들은 자기 조작을 우선한다.
- 임계값은 위 소스값을 무조건 복제하지 말고 OS/화면/터치 컨트롤에 맞춰 검증한다.

추천 작업 순서
1. 포커스 대상 좌표/메뉴 수명주기/권한별 액션 모델.
2. 터치 시작 영역과 방향을 공유하는 제스처 조정; 답장 방향과 빈 배경 뒤로가기를 분리.
3. 반응 취소/교체/카운트와 낙관적 표시, 복구·멀티기기 반영.
4. 실제 다중 선택 모드, 이후 접근성·텍스트 부분 선택·추가 미디어 액션.

검수 사례
- 짧은 메시지 오른쪽 여백에서 시작한 드래그가 옆 메시지 답장이 되지 않는다.
- 같은 메시지 왼쪽 스와이프는 답장, 빈 배경 오른쪽 스와이프는 뒤로가기만 실행된다.
- 천천히 세로 스크롤/대각선/빠른 플릭/임계값 직전 취소를 각각 확인한다.
- 사진 앨범의 넘기기와 음성 재생바 조작은 답장·뒤로가기에 빼앗기지 않는다.
- 포커스 메뉴 중 수신/해당 메시지 삭제/키보드 열림/방 전환을 검사한다.
- 메뉴 닫기 후 기존 읽던 위치가 유지되고 미디어 다운로드·읽음이 중복 실행되지 않는다.
- 반응 재선택 취소/변경/오프라인 실패/두 기기 동시 반응을 확인한다.
- 다중 선택 중 답장 스와이프가 실행되지 않고 선택 개수와 일괄 액션이 일치한다.
