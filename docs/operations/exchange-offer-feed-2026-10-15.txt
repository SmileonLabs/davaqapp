DavaQ exchange offer feed — 2026-10-15

Production deployment and client release
The Exchange tab now points to ExchangeFeedScreen. The old /tcg/market route remains available for the map and legacy links. The production API and web/PWA were deployed on 2026-10-15. Existing app IDs, user/card/chat ownership, production domain and signing identities are preserved. Final native targets are iOS 1.0.0 (24) and Android 1.0.0 (34). See the release status below for actual store availability.

Interaction
- Vertically paged cards with a measured fixed page size, one scroll owner, stable card IDs and virtualized rendering. Initial render: 3; viewport window: 5. Native paging and web CSS scroll snapping share the same layout.
- Register a specific-card swap, open proposals or a free giveaway. Existing collection photos remain the actual seller photos; a duplicate active listing routes to management.
- Like, comment and propose from sheets; sheets respect safe areas and preserve the feed position on dismissal. Comments page in batches of 50. Offers use current available quantity/version and stable request keys; giveaways do not send an offered card or payment.
- Existing transaction locking/reservation logic protects acceptance and prevents duplicate allocation. Proposals alone do not reserve stock.

Full-screen visual update
- Card photography occupies the entire viewport. The original image is contained without cropping; a blurred cover of the same resolved URI fills the remaining background. Dark gradients keep the overlaid header, captions, social actions and transaction button readable.
- Twenty editable SVG assets live in artifacts/mobile/assets/icons/exchange/. ExchangeIcon provides consistent optical size, 1.9px rounded strokes and currentColor. The exchange screen and five tab controls use actual vector paths instead of text symbols or icon-font glyphs.
- Likes have outlined/filled states, spring press feedback and native selection haptics. Share uses the system share flow or the browser share/clipboard fallback only after a user press.
- Exchange tab navigation becomes transparent with light icons. A focused light status bar and native safe-area offsets keep system controls clear; PWA sheets include the standalone bottom inset.
- Compact and short viewport layouts reduce caption density and reposition social/photo controls to prevent overlap. Preview checked at 390x844, 375x667, 844x390 and desktop, including photo arrows, filled like state, sheet close controls and 720px card scroll snapping.
- Foreground and blurred backdrop share one URI resolution and cache entry. They are two image views, so physical-device decode/GPU cost still requires release testing. Native retry waits for authorization refresh before remounting the image.

Loading and cache
- Failed explicit refresh restores previously loaded pages and the viewing position; expired cursors prompt a fresh feed instead of repeated retries.
- Warm the first 20-card page and first 3 representative photos after authenticated tab startup, before the Exchange tab is opened.
- Prepare the current photo, next 3 and previous 1. Speculative image work has concurrency 2 and a bounded 80-path completion history. Mounted visible views can additionally load images needed for display.
- Prepare another 20-card page with 10 cards remaining. Late warmup cannot replace the active swipe window. Rapid swipes replace pending work; hidden/background/offline sessions stop starting speculative work.
- Query keys include the account, search and card filter. Abort signals protect fetch lifecycle; query cache expires after 5 minutes without observers. Metadata pages are retained while browsing so swiping back does not lose cards.
- Native prefetch and display share the same media-url query and exact signed URL, with expo-image memory/disk cache. Invalid/expired addresses have visible retry and request a fresh address. No image is rendered before a usable native URI exists.
- PWA private photos share the existing account-specific blob cache (80 photos, 64 MiB, 7 days; logout/account-switch cleanup). Public thumbnails use browser image caching. No new service-worker cache of private images was added.

API and database
- Legacy public /api/tcg/listings keeps swap/both only; new giveaways are exposed by the new feed and the owner listing manager.
- GET /api/tcg/feed?cursor=&q=&cardId= returns 20 items and nextCursor; items include offer_count, like_count, comment_count, liked_by_me, can_offer.
- PUT /api/tcg/listings/:id/like {liked}; GET/POST /api/tcg/listings/:id/comments. Writes are authenticated, blocked-user visibility is respected, and comments have length/rate/idempotency checks.
- Migration 0043_davaq_tcg_offer_feed.sql preserves old data, adds gift mode, social tables/indexes and owner/search-scoped 30-minute feed snapshots.
- First load snapshots the set of cards with currently active proposals. Accepting/cancelling an offer does not reorder later pages. Explicit refresh creates a new snapshot, excluding expired/closed proposals from priority.
- A materialized 21-row page bounds per-card statistics work; only 20 rows are returned. A missing/expired/mismatched snapshot returns 410. The client offers a new feed rather than endlessly retrying that cursor.

Registration and sign-in follow-up
- Home leads to browsing; registering a card is optional. An empty public feed explains the absence of listings and offers a catalog browse action without forcing ownership registration.
- Owning a card and publishing a trade are explicit separate steps. Successful save updates the scoped account cache and waits for refresh before navigation. Publishing from an offer returns to the same target with the new offered card selected.
- The saved-card photo editor preserves the publish/offer intent and returns directly to the selected card's publish screen. Success notices expire instead of obstructing the feed.
- The sign-in/sign-up entry offers Google and Apple only. Legacy installed-client server login compatibility is retained.
- A provider subject mapping is authoritative. A newly verified, exact normalized email may link to exactly one existing database user; id, clerk_id, nickname, cards and chat ownership are retained. Provider/email transaction locks avoid concurrent duplicate accounts; ambiguous or unverified matches are refused.
- Unknown Apple private-relay addresses are not guessed or merged. An authenticated existing member can explicitly link Apple in settings.
