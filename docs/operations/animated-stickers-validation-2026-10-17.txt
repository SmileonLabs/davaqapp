애니메이션 스티커 확장·로딩 개선 / 2026-10-17

확인한 지연 경로
기존 선택기는 ScrollView를 열면서 원격 512px animated WebP 40개를 모두 마운트했다.
해당 40종의 원본 합계는 약16.64MB였다. 첫 로딩은 CDN/네트워크/이미지 디코딩에 의존했다.
실기기의 열림 시간이나 FPS는 이번 작업에서 직접 측정하지 않았다.

변경
- Google Noto Animated Emoji 공식 목록에서 실제 다중 프레임 WebP 212종을 추가했다.
  기존 40종을 모두 유지하고 172종을 늘렸다. 정적 유니코드 그림으로 교체한 것이 아니다.
- 표정·마음69 / 동물·자연32 / 음식24 / 축하·활동24 / 사물24 / 기호16 / 여행16 / 사람3 / 깃발4.
- 한 번에 12개씩 재생하며 이전/다음으로 탐색한다. 분류와 검색을 제공한다.
  화면 밖 전체 스티커를 동시에 내려받거나 재생하지 않는다.
- 128px 애니메이션을 앱 asset으로 포함한다. 설치된 네이티브 릴리스에서 선택기를 열 때
  해당 212종을 외부 CDN에서 가져올 필요가 없다. 개발 빌드는 Metro에서 asset을 받을 수 있다.
  웹은 동일 출처 asset을 첫 요청/캐시로 제공하므로 처음부터 완전 오프라인이라는 뜻은 아니다.
- 동일한212종의 원본 합계97.19MB → 최적화25.09MB, 74.2% 감소.
  이것은 원본과의 비교다. 앱 설치 자원에는 약25.09MB가 추가되는 비용이 있다.
- 크기 축소 및 인접 프레임 묶음을 적용했다. 반복·투명 배경·전체 재생 시간을 유지했다.
  생성 시 모든 파일을 Pillow로 디코딩해 다중 프레임 및 전체 재생 시간을 확인했다.
- 알려진 스티커는 메시지 본문/반응에서도 같은 로컬 자원을 쓴다.
  과거 메시지에 남아 있는 팩 밖 코드는 기존 CDN fallback을 유지한다.
- code가 바뀌면 이전 이미지의 실패 상태를 초기화한다. 불필요한 이미지 fade 지연을 없앴다.
- 스티커 메시지 code/type, 전송/outbox, 변경 로그, 재접속/읽던 위치 저장은 변경하지 않았다.
  서버 API 변경이나 DB 마이그레이션은 필요 없다.

실기기 확인
1. 이번 코드와 asset을 포함한 새 네이티브 빌드를 설치한다. 기존 설치본에는 새 팩이 없다.
   cd /Users/smileonlabs/Documents/davaq
   source .local/activate.sh
   pnpm --filter @workspace/mobile exec expo run:ios --device
   또는 pnpm --filter @workspace/mobile exec expo run:android --device
2. iOS/Android 각각 입력창의 스티커 버튼을 처음 연다. 첫12개가 실제로 움직이는지 확인한다.
   분류/다음/이전/검색을 반복하고 마지막 페이지까지 정상 선택되는지 확인한다.
3. 새 동물·음식·활동 스티커를 하나씩 보내고 상대 기기에서도 움직이는지 확인한다.
   기존 스티커와 반응의 취소·집계도 확인한다.
4. 오프라인 확인은 로컬 asset이 설치된 Release 빌드에서 한다. 앱 종료→비행기 모드→
   재실행→아직 열지 않은 분류로 이동한다. 애니메이션이 보여야 한다.
   개발 서버가 필요한 Debug 빌드/Expo Go로 이 오프라인 조건을 판정하지 않는다.
5. 연결을 끊고 스티커 하나를 전송한 뒤 앱 종료→재연결한다. 상대에게 정확히1개 도착하고
   과거 대화의 읽던 위치가 복원되는지 확인한다.
6. 동일 기기·동일 빌드 종류에서 처음 열기/두 번째 열기를 구분해 화면 녹화한다.
   남은 지연이 있으면 기종/OS/분류/첫 열기인지/발생 시각을 기록한다.
