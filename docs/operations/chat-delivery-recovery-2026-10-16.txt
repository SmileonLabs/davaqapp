DavaQ 메시지 전달·전체 변경 복구 구현 — 2026-10-16

상태
- 로컬 코드 구현과 격리 테스트 완료. 운영 서버/DB에 적용하지 않았다.
- 기존 작업 폴더의 미커밋 변경을 보존했다. 이 작업으로 별도 커밋이나 배포를 만들지 않았다.

저장과 전달
- 0046_chat_change_delivery.sql은 chat_sync_rooms, chat_changes,
  chat_delivery_outbox와 지연 실행되는 제약 트리거를 추가한다.
- messages의 생성/수정/삭제, 개인 삭제, 반응, 링크 미리보기,
  멤버/읽음 변경, 방 메타데이터 변경을 기존 데이터 변경과 같은 트랜잭션으로 기록한다.
- 방별 revision 행의 잠금이 커밋까지 유지된다. 단순 전역 sequence와 달리,
  커서보다 낮은 순번의 미커밋 변경이 뒤늦게 나타나서 건너뛰어지는 일을 방지한다.
- 채팅방 메시지 미리보기/순번 카운터만 바꾸는 UPDATE와 실제 변화 없는
  UPDATE는 불필요한 방 변경 이벤트를 만들지 않는다.
- 일반 HTTP 메시지 전송과 전달(forward)은 수신자별 푸시 작업도 같은 트랜잭션에 저장한다.
  clientMessageId의 기존 중복 방지와 push:<messageId>:<recipientId> 고유 키를 유지한다.
- 빠른 화면 표시를 위한 기존 실시간 발행은 유지된다. 영속 작업자의 재발행과
  겹칠 수 있으므로 수신 측 메시지 ID 병합과 변경 커서로 중복을 처리한다.
- 실시간/푸시 채널의 작업 루프를 분리해 푸시 제공자 정지가 실시간 발행을 막지 않는다.
- API 작업자는 SKIP LOCKED로 작업을 획득하고 60초 임대/claim token을 사용한다.
  만료된 임대를 다시 획득할 수 있고, 이전 작업자의 늦은 완료는 새 임대를 덮지 못한다.
- 외부 전달은 30초 후 재시도 상태로 전환하고, 실패 시 2~256초의 제한된 지수 지연을 적용한다.
  전달 성공 뒤 DB 완료 기록에 실패해도 임대 만료 후 재처리한다.
- durable 실시간 발행은 Redis 실패를 로컬 성공으로 대체하지 않는다.
  푸시는 strict 모드로 APNs/FCM/Web 오류를 전달하며 기존 호출자는 best-effort 동작을 유지한다.
- 전달 시 멤버십·차단·음소거·읽음·전체/개인 삭제를 다시 확인한다.
- 완료한 outbox 작업은 payload를 비워 알림 본문을 중복 보관하지 않는다.

재접속 API와 앱
- GET /api/rooms/:id/changes: afterRevision을 생략하면 최근 50개와 동일 스냅샷의
  변경 순번/메시지 순번 상한을 반환한다. 이후에는 200개 이벤트 단위로 차이를 반환한다.
- 변경 목록과 메시지 본문은 REPEATABLE READ 트랜잭션으로 읽는다.
  기존 직렬화기를 사용하므로 개인 삭제, 공개 프로필, 미리보기 보안 정책을 유지한다.
- 개인 변경은 당사자에게만 반영한다. 다른 사람의 개인 이벤트를 건너뛰어도
  페이지 커서는 전진하므로 빈 페이지로 복구가 멈추지 않는다.
- 오래된 메시지 변경도 ID로 조회한다. 최근 50개 밖의 삭제/반응을 놓치지 않는다.
- 앱은 결과가 Query 캐시에 반영된 뒤에만 변경 커서를 전진시킨다.
  취소·네트워크·인증·서버 오류는 커서를 전진시키거나 부분 복구로 대체하지 않는다.
- 캐시의 실제 Query 객체에 수신 상태를 연결한다. 방을 다시 열면 동일 캐시의 커서를
  재사용하지만, GC/앱 재시작으로 캐시를 잃으면 새 스냅샷으로 시작한다.
- 지연된 이전 HTTP 응답이 삭제/반응을 되돌리지 않도록 authoritative overlay를 적용한다.
  로컬 삭제 대기 행을 다시 만들지 않고, 로드하지 않은 과거 변경을 갑자기 목록에 끼워 넣지 않는다.
- hasMore이면 계속 복구하고, 읽음/방 변경은 방 목록·배지도 갱신한다.
- 구버전 서버가 새 경로에 404를 반환하는 경우에만 기존 roomSeq 복구로 호환한다.
  기존 메시지 API, 전송 대기열, 읽음 추적, 푸시 경로는 유지한다.
- OpenAPI에 새 경로/응답과 생성된 클라이언트·Zod 계약을 추가했다.
  기존 명세와 생성물 사이에 있던 지도/거래 관련 차이는 이 작업에 섞지 않았다.

적용 순서
1. DB 백업/복구 지점과 기존 배포 절차를 확인한다.
2. 기존 마이그레이션 절차로 0046을 먼저 적용한다.
   런타임 서버 시작 시 DDL을 실행하지 않는다. drizzle push만으로는 SQL 트리거가 설치되지 않는다.
3. 새 API 이미지를 배포한다. 시작 시 outbox 작업자가 자동 실행된다.
4. PWA/모바일 코드를 배포한다. 구버전 앱의 기존 HTTP/실시간 계약도 계속 동작한다.
5. 테스트 계정 두 기기로 연결 끊김/재접속/읽음/개인 삭제/전달을 운영과 같은 환경에서 확인한다.

롤백
- 앱/API 이미지 롤백 시 새 테이블·로그·트리거를 삭제하지 않는다.
  구버전 API도 기존 데이터 쓰기를 계속할 수 있고 변경 로그는 남는다.
- 새 작업자를 모두 내리면 미완료 작업은 DB에 대기한다. 새 작업자를 복구하면 재개된다.
- 구버전 앱/API만으로는 새 변경 로그 프로토콜의 복구 보장을 제공하지 않는다.
- 이번 작업에서는 자동 로그 삭제를 추가하지 않았다. chat_changes를 임의로 삭제하면
  오래된 커서의 연속성이 깨질 수 있으므로, 향후 retention/floor/reset 정책과 함께 도입해야 한다.

운영 조회 예시 (본문/사용자 토큰을 출력하지 않음)
SELECT channel, count(*) AS pending, min(created_at) AS oldest,
       max(attempts) AS max_attempts
FROM chat_delivery_outbox WHERE delivered_at IS NULL GROUP BY channel;

SELECT channel, count(*) AS repeatedly_failed
FROM chat_delivery_outbox WHERE delivered_at IS NULL AND attempts >= 10 GROUP BY channel;

SELECT count(*) AS expired_leases FROM chat_delivery_outbox
WHERE delivered_at IS NULL AND lease_until < now();

검증 범위
- PGlite의 PostgreSQL 엔진으로 실제 마이그레이션/트리거/트랜잭션/작업 SQL을 실행했다.
  커밋 전 롤백, 중복 요청, 커밋 후 미발행, 전달 실패, 전송 후 DB ack 실패,
  임대 만료/이전 작업자 fencing, 외부 제공자 정지, 1,005개 이벤트 페이지 복구,
  개인 이벤트 필터, 멤버/프로필 권한, 전체/개인 삭제·반응·미리보기·읽음·핀을 확인했다.
- Redis 실패의 durable/best-effort 구분, 푸시 strict 실패 전파와
  읽음/삭제/차단/음소거 후 지연 푸시 억제를 mock 제공자로 검증했다.
- 클라이언트는 취소 시 커서 유지, 중복 변경, 늦은 HTTP 응답, 빈/개인 필터 스냅샷,
  캐시 GC 뒤 재기준화, 방 재진입, 1,201건 페이지 적용, 기존 전송/알림 회귀를 확인했다.
- 운영 Redis/APNs/FCM에 장애를 주거나 실제 프로세스를 kill하지 않았다.
  독립 PostgreSQL 연결들의 동시 커밋/실제 네트워크 분할/실기기 푸시는 별도 환경 검증이 필요하다.
- 보장은 DB 기록과 작업 재시도 및 재접속 최종 일치다. 외부 알림과 WebSocket은
  at-least-once이므로 제공자 수락 직후 종료되면 중복 전달될 수 있다.
  OS가 알림을 실제 표시했다는 exactly-once 보장은 아니다.
- AI 턴 작업 자체와 통화 시그널 작업의 영속화는 이번 채팅 전달 범위에 포함하지 않는다.
- 전체 OpenAPI 경로 커버리지 검사는 기존 소셜 인증·그룹 통화·카드/신고 경로 등
  29개 미문서화 경로 때문에 실패한다. 새 /rooms/{id}/changes는 명세에 포함되어 있다.
