Telegram 비교: DavaQ 렌더링·사용 경험 개선안
작성: 2026-10-17 / 구현·배포 변경 없음

결론
가상화나 이미지 캐시는 이미 있다. 다음 투자는 과거 대화 탐색과 읽던 위치 복원,
변경된 행만 렌더링하는 구조, 이미지 높이 안정화, 진입·키보드 전환의 연속성에 둔다.
메시지 전달 P0/P1/P2 작업과 별개인 UI 개선 우선순위다.

분석 범위와 신뢰도
- 실제 실행: 공식 npm rea-agents 6.5.0 CLI. 전역 MCP 설정은 변경하지 않았다.
- Telegram Web A 공개 소스 commit f67a40879a7d78c2683ec5a296cf55bc22417d56.
  메시지 목록, 스크롤, 관찰자, 애니메이션, 미디어, 초안 관련 8개 파일을 REA로 파싱.
  8개 성공, 파싱 실패 0. 선택하지 않은 파일 913개이므로 전체 그래프 커버리지는 partial.
  REA의 findings 개수는 성능 문제 개수가 아니다.
- 설치된 macOS Telegram 13.0(283305)은 REA로 arm64 dylib 의존성을 정적 확인했다.
  AppKit/QuartzCore/Metal 등의 의존성이 있다는 사실만 확인하며, 이것으로 특정 효과의
  구현이나 iOS/Android 렌더링 경로를 입증하지 않는다.
- Telegram iOS ListView/ChatHistoryListNode 및 Android RecyclerListView 공개 소스도 참고.
  배포된 모바일 빌드와 공개 소스가 동일하다고 검증한 것은 아니다.
- DavaQ 작업 트리의 실제 코드와 대조했다. FPS·메모리·터치 지연 실측은 하지 않았다.
  아래 결함 위험은 정적 근거와 검증할 가설을 구분한다. 기존 실기기 전달/푸시 검증은
  이번 렌더링 성능 검증을 대신하지 않는다.

이미 갖춘 기반 — 유지할 것
- chat/[id].tsx: FlatList 가상화, 네이티브 inverted, maintainVisibleContentPosition,
  12개 초기 렌더링, batch8/window7, clientMessageId 기반 키.
- MessageBubble/MessageComposer/Inbox RoomRow: React.memo.
- ChatCachedImage: 계정별 안정 캐시 키, memory-disk, 미리보기, 만료 URL 재발급.
- 최신 메시지 로컬 복원, 영속 송신 대기열, 재접속 변경 복구.
- 초안 로컬 저장, 답장 스와이프, 읽음 추적, 새 메시지 표시와 하단 이동 제어.
따라서 '메모이제이션/가상화/캐시를 처음 도입'하는 제안은 적절하지 않다.

우선순위 1: 과거 대화 페이지 로딩과 읽던 위치 복원
확인: 첫 진입은 최신50개, 영속 히스토리는 방당 최대500개다. 현재 채팅 화면 및
메시지 훅에서 과거 방향 로딩을 호출하는 경로/onEndReached를 찾지 못했다.
useReliableRoomMessages는 과거 방향 페이지 로딩을 별도 경로의 책임으로 명시한다.
useInvertedChatListController는 방 진입 시 최신 위치로 초기화한다.
Telegram 근거: MessageList가 loadViewportMessages(Around)와 메시지 anchor를 사용한다.
개선: beforeSeq 등 서버 지원을 먼저 확인하고 과거50개씩 로드, 첫 보이는 메시지ID+
픽셀 오프셋 보존. 방 재진입은 '마지막 읽던 위치/미확인 시작/최신'을 정책으로 구분.
답장·핀·검색 결과가 캐시 밖이면 해당 메시지 주변을 가져온 뒤 이동한다.
완료 기준: 1만개 방의 과거 메시지·답장 이동 가능, 앞쪽 로딩과 재접속 중 읽던 행 유지.
주의: 방당500개 캐시 제한을 무조건 늘리거나 전체 이력을 한 번에 내려받지 않는다.

우선순위 2: 기존 말풍선의 불필요한 렌더링 억제
확인: renderMessageItem이 listMessages/albumGroups 전체에 의존하고, 각 행에
onPressReply 인라인 함수를 넘긴다. MessageBubble은 기본 shallow memo이므로 새 함수는
메모 경계를 깨뜨릴 수 있다. 전체 목록 변경이 기존 행에 퍼질 위험이며 실측 필요.
Telegram 근거: Web A의 memo 경계·별도 목록 콘텐츠, iOS의 행 단위 갱신/레이아웃 적용.
개선: memo된 MessageRow로 행 계산 분리, ID별 안정 데이터 참조/콜백, 앨범 그룹 계산
증분화. 읽음·선택·입력·존재 상태를 필요한 행/작은 하위 뷰만 구독하도록 정리.
완료 기준: 입력100타 동안 이력 말풍선 재렌더0회, 메시지1개 추가 시 변경 행과
인접 그룹 경계 외 기존 행의 재렌더가 없는지 프로파일러로 검증.
주의: 사용자 정의 비교 함수로 실제 편집·삭제·읽음 갱신을 누락시키지 않는다.

우선순위 3: 사진 로드 전후 높이와 작업 우선순위 안정화
확인: 이미지 메타데이터로 초기 비율을 주지만 MessageBubble의 onLoad가 aspect를
다시 변경한다. 치수가 없는/틀린 과거 데이터에서는 행 높이가 바뀔 수 있다.
ChatCachedImage는 캐시가 있어도 마운트 시 미디어 주소 훅을 호출하며, 화면 가시성에
따른 다운로드/디코딩 우선순위 입력은 현재 컴포넌트 인터페이스에 없다.
Telegram 근거: Web A useMedia는 noLoad로 로딩을 제어하고 메모리 값을 먼저 조회한다.
개선: 업로드 시 정규화된 치수 저장, 고정 프리뷰 상자, 메타데이터 불일치 보정 시
anchor 보존. 현재 화면/인접 영역부터 준비하고 먼 화면은 요청·디코딩을 지연.
완료 기준: 사진50개 스크롤에서 완료 시점의 읽던 행 이동 최소화, 화면 밖 로딩
동시성 제한, 사진 왕복 열기 시 메모리 증가가 지속되지 않는지 실측.
주의: 이미 있는 계정별 캐시 격리·접근권한 검사·만료 URL 갱신은 유지한다.

우선순위 4: 방 진입과 키보드 전환을 하나의 시각적 동작으로 처리
확인: 목록은 listReady 전 opacity0이며 초기 위치 결정에 연속 requestAnimationFrame을
사용한다. 네이티브 화면 패널은 준비 후220ms 이동 애니메이션. 키보드 didShow/didHide
이후 별도 하단 보정도 있어 비동기 콘텐츠 측정과 겹칠 가능성이 있다.
Telegram 근거: Web A는 무거운 애니메이션 중 observer 처리를 얼렸다가 합쳐 적용한다.
fasterdom은 레이아웃 측정과 변경을 별도 단계로 처리한다. 웹용 원칙을 네이티브에
그대로 복사하기보다 네이티브 UI 스레드/키보드 컨트롤러에 맞춰 적용한다.
개선: 캐시된 첫 화면을 먼저 보여주고 최신화는 뒤에서 처리. 위치 보정·키보드 inset·
새 메시지 수신을 단일 조정 경로로 합치고 읽는 중이면 강제 하단 이동 금지.
완료 기준: 캐시 방의 읽기 가능한 첫 화면 p95 200ms 이내를 초기 목표로 설정,
키보드 열고 닫기20회/사진 로딩/수신 동시 상황에서 점프와 입력 가림 없음.
목표 수치는 Telegram 실측값이 아니라 DavaQ의 제안 검수 기준이다.

우선순위 5: 복구 상태를 이해할 수 있는 메시지 전송 UX
확인: pending은 '전송 중', 실패는 '전송 실패'와 재전송·취소를 표시한다.
현재 채팅 화면에서 네트워크 오프라인 대기와 서버 처리 지연을 구분하는 표시는
확인하지 못했다. 백엔드 복구가 있어도 사용자는 실패인지 대기인지 알기 어렵다.
개선: '연결 중/오프라인 — 연결되면 자동 전송/전송 실패'를 구분하고 기존 버블 안의
작은 상태만 갱신. 재접속 시 목록 초기화·새 메시지 애니메이션 일괄 재생 금지.
완료 기준: 비행기 모드→앱 종료→복귀에서 같은 버블이 유지되고 중복 전송/새 방 이동
없이 상태만 변함. 실제 발송 취소 가능 시점과 이미 발송된 상태를 명확히 구분.

우선순위 6: 초안을 대화 목록과 여러 기기에서 이어쓰기
확인: MessageComposer가 텍스트를300ms debounce 및 unmount에 로컬 저장한다.
초안 저장소는 AsyncStorage이고 Inbox의 미리보기는 lastMessage다. 현재 확인한
경로에는 서버 초안 동기화나 대화 목록 초안 표시가 없다.
Telegram 근거: Web A useDraft는 chat/thread 범위의 saveDraft/clearDraft 액션과
백그라운드·화면 종료 처리를 연계한다. 서버 저장 세부 구현은 이번8파일 범위 밖이다.
개선: 목록에 '초안' 표시, 답장 대상·첨부 준비 상태 포함 복원. 서버 동기화는 버전/
충돌 정책과 현재 기기 입력 보호를 먼저 설계한다. 오프라인 송신 큐와 초안은 구분.
완료 기준: 두 기기가 동시에 입력해도 현재 입력을 덮어쓰지 않고 계정 전환 시 분리.

우선순위 7: 메시지 탐색·작업과 접근성 완성도
확인: 핀 이동·답장·길게 누르기와 일부 접근성 라벨은 이미 있다. 캐시 밖 이동을
완성하고, 사진 열기/복사/전달/편집 같은 액션의 우선순위를 실제 메뉴 기준으로 점검.
제안: 대화 내 검색→결과 주변 로딩→강조→원래 위치 복귀를 한 흐름으로 만든다.
VoiceOver/TalkBack에서 발신자·본문·시간·상태를 묶어 읽고 큰 글씨/동작 줄이기를 지원.
검수: 최대 글꼴, 긴 한국어/URL, 이미지 캡션, 한 손 조작, 화면 읽기 도구로 테스트.
이는 전체 액션의 부재를 단정하는 항목이 아니라 후속 UX 검증 과제다.

추천 실행 순서와 검증
1. 전용 테스트 방에서 변경 전 측정: 1만개 텍스트, 사진50개, 앨범, 긴 문장.
2. 과거 방향 로딩+anchor 복원, 행 렌더링 격리부터 작은 변경으로 적용.
3. 이미지 높이/우선순위, 방 진입/키보드 조정, 복구 상태 표시 순으로 적용.
4. 초안 동기화·검색·접근성은 기능 설계와 함께 진행.
5. iPhone13Pro와 GalaxyS20급에서 release 빌드로 각 시나리오30회 측정.
   60Hz 프레임 예산16.7ms, 120Hz8.3ms를 기준으로 JS와 UI 스레드를 별도 관찰.
   느린 프레임 비율·입력 표시 p95·방 첫 화면 p95·RSS/heap·이미지 메모리를 기록.
   입력 표시 p95 50ms, 정상 스크롤 느린 프레임1% 미만은 초기 제안 목표이며
   동일 조건의 baseline을 얻은 뒤 조정한다. RN 단위의 레이아웃 이동은 같은 행의
   화면좌표 차이로 측정하며 웹 CSS pixel과 혼합하지 않는다.
기존 chatPerformanceDiagnostics는 렌더 횟수와 입력/ACK 표본에 재사용할 수 있으나
browser localStorage로 활성화하며 DOM/JS heap 중심이다. 네이티브는 별도 활성화와
UI frame/RSS 계측 연결이 필요하다. ACK 지연과 첫 버블 표시 지연도 따로 측정한다.
기존 유실·중복 방지, 재접속 복구, 멀티기기·백그라운드 푸시는 회귀 검증에 포함한다.
FlatList→FlashList 전환이나 네이티브 전면 재작성은 위 측정 후 병목이 남을 때 판단.
