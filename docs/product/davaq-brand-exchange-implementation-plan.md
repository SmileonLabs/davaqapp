# DavaQ 브랜드 교환 구현 계획

작성일: 2026-09-12. 상태: 구현 전 설계안. 이 문서는 현재 서비스를 변경하거나 캠페인을 개설하지 않는다.
기준: 현재 DavaQ PWA, 별도 DavaQ 저장소 및 [MVP 운영 기록](../operations/davaq-exchange-mvp-20260912.md).

사용자는 약 1분의 영상 비교 참여를 광고주가 제공하는 쿠폰·상품 교환권·체험권과 교환한다. Q는 사용자가 원하는 보상을 가진 실제 캠페인을 추천한다. 사용자가 직접 참여하며, 성공 조건 검증과 지급은 서버가 처리한다.

**1. 첫 출시 범위**

| 구분 | 첫 출시 | 후속 확장 |
| --- | --- | --- |
| 보상 | 확보된 쿠폰, 매장 상품 교환권, 디지털 체험권 | 직접 배송 상품, 복수 공급사 실시간 발급 |
| 광고 운영 | 운영자가 광고주를 대신해 캠페인 등록·검수·보고 | 광고주 셀프 등록·결제·소재 제작 도구 |
| 게임 | 원본·변형 영상 동시 재생, 차이 2~3개, 정해진 재도전 정책 | 순차 재생, 주간 기획전, 다양한 난이도 |
| 추천 | 사용자가 고른 희망 보상·지역과 동의한 개인화 정보 | 더 정교한 추천·재방문 실험 |
| 획득 후 | 내 혜택 보관·사용·문제 신고 | 양도 허용 이용권의 다른 사용자와 재교환 |

첫 버전의 캠페인 조건 예시는 ‘30초 영상 두 개 동시 재생, 차이 2개, 안내·결과 포함 약 1분’이다. 동시 재생 30초를 시청 60초로 집계하지 않는다. 재도전은 추가 시간이 든다는 점을 시작 전에 표시한다. 보상 종류와 금액은 실제 공급 계약과 광고주 예산으로 확정한다.

기존 EV는 교환가치 참고값으로 유지한다. 광고 보상은 별도의 혜택이며 EV 적립·충전·현금 출금이나 사용자 간 차액 결제로 연결하지 않는다. 신규 사용자도 내 교환 등록 없이 브랜드 교환에 참여할 수 있다.

**2. 사용자 흐름과 화면**

기본 흐름: Q 추천 또는 목록 탐색 → 조건 확인 → 보상 수량 확보 → 영상 비교 → 서버 성공 판정 → 보상 지급 → 내 혜택에서 사용.

| 화면 | 구현 내용 |
| --- | --- |
| 홈 | ‘내 1분 바꾸기’ 영역. 브랜드·보상·예상 시간·광고 표시가 있는 카드. 유효 캠페인이 없으면 거짓 예시로 채우지 않음 |
| 둘러보기 | ‘브랜드 교환’ 선택. 쿠폰/상품 교환권/체험권, 지역·온라인·시간·사용 조건 필터 |
| 캠페인 상세 | 내가 제공할 참여와 받을 보상, 성공 기준, 재도전, 사용 기한, 추가 구매·배송비 조건, 지급 시점, 광고주·문의처 |
| 영상 비교 | 두 영상, 하나의 진행 바, 찾은 차이 수, 남은 도전, 중단 버튼. 정답 영역 터치 피드백 |
| 참여 결과 | 성공·미완료·검증 대기·지급 대기·지급 완료를 구별. 지급 대기 시 다시 광고를 보게 하지 않음 |
| 채팅/Q | 실제 캠페인 카드와 추천 이유. 사용자 요청 또는 별도 허용한 추천 범위에서 제시. 퀴즈 정답·자동 참여 기능 없음 |
| 내 교환 | ‘받은 혜택’ 진입. 미사용·처리 중·사용 완료·만료·문의 중 상태 |
| 혜택 상세 | 쿠폰/바코드, 발행처·사용처·조건·기한, 사용 상태, 문제 신고. 코드 노출은 소유자만 가능 |
| 내 AI | 브랜드 개인화 설정, 직접 확인한 보상 취향, 실제 참여·사용에 따른 발견 배지 |
| 운영 화면 | 캠페인·영상·정답·재고·예산·발급 실패·문의·집계 관리 |

기존 홈 / 둘러보기 / 채팅 / 내 AI / 내 교환 다섯 메뉴를 유지한다. 일반 채팅이나 사용자 간 교환을 계속하려면 광고를 보아야 하는 구조는 넣지 않는다. Q가 추천한 모든 유료 캠페인에는 ‘광고 · 브랜드 교환’을 표시한다.

**3. 영상 비교 게임**

광고주는 원본과 변형본을 제공하거나 운영자가 허락받은 원본으로 변형본을 제작한다. 첫 버전에는 생성형 영상 자동 제작이 필요하지 않다. 운영자가 변경 객체의 재생 시간 구간과 정규화 좌표를 등록하고 광고주가 검수한다. 가격·효능·주의사항을 오해하게 하는 변형은 사용하지 않는다.

두 영상을 같은 시점으로 재생하며 소리는 원본 한쪽에서만 출력한다. 클릭으로 재생을 시작하고, 한쪽이 버퍼링하거나 화면이 백그라운드로 전환되면 양쪽 진행을 함께 멈춘다. 복귀 후 동기화와 이어보기를 지원한다. 다른 탭과 중복 실행할 때는 한 참여 세션만 유효하게 한다.

정답 판정은 실제 영상이 표시되는 영역의 좌표와 재생 시각을 기준으로 한다. 화면 확대·회전·영상 여백을 고려한다. 성공은 정해진 재생 구간 완료와 정답 조건 충족이 모두 확인됐을 때다. 마지막 차이는 후반부에도 배치할 수 있지만 참여 조건을 사후 변경하지 않는다. 검수된 난이도와 충분한 터치 영역을 사용한다.

브라우저의 재생 종료 이벤트 하나만으로 지급하지 않는다. 서버 발행 참여 ID·캠페인 버전·시도별 토큰, 순서가 있는 진행 이벤트, 경과 시간, 정답 시점·좌표를 함께 검증한다. 반복 전송은 같은 사건으로 처리하며, 새로고침으로 도전 횟수가 초기화되지 않게 한다. 정답 좌표와 쿠폰 원문은 공개 API·프론트 번들·Q 프롬프트에 포함하지 않는다.

이 검증은 부정 참여를 줄이는 장치다. 사용자의 실제 시선·인지 또는 사람만의 참여를 완전히 증명한다고 표시하지 않는다. 카메라 감시는 요구하지 않는다. 초기에는 사용자별 지급 한도·동시 세션 제한과 운영 검토로 위험을 제어한다.

**4. 보상 수량·예산·지급**

캠페인에는 전체 수량, 일일 한도, 사용자별 한도, 지급 조건, 보상 만료 정책, 운영 비용 한도를 설정한다. 광고주 대금 확인과 보상 재고 확보가 끝난 캠페인만 공개한다. 금전 예산은 광고 운영 장부이며 사용자 EV와 분리한다.

참여 시작 시 DB 트랜잭션에서 보상 1개와 필요한 예산을 확보한다. 마지막 재고에 동시에 접근해도 성공 조건을 충족한 사람에게 약속한 보상이 부족하지 않도록 한다. 만료된 쿠폰이나 남은 사용 기간이 너무 짧은 쿠폰은 재고로 제공하지 않는다.

영상 재생 도중 캠페인 예산이 소진돼도 이미 확보한 정상 참여의 조건은 유지한다. 일반 중단은 새 참여만 차단한다. 권리·안전상 긴급 중단은 별도 운영 상태로 기록하고 진행 중 사용자에게 안내한다. 최종 시도 미완료·명시적 중단·복구 유예 종료 시에만 미지급 예약을 해제한다. 검증·지급 중인 보상은 단순 타임아웃으로 다른 사람에게 배정하지 않는다.

| 참여 상태 | 의미 |
| --- | --- |
| 확보됨 | 보상과 참여 조건 버전이 고정됨 |
| 재생 중 / 일시 중지 | 유효 시도와 재생 증거 수집 |
| 검증 중 | 정답·재생·한도·이벤트 중복 확인 |
| 성공 | 보상 받을 권리 확정 |
| 미완료 / 중단 / 만료 | 정해진 조건에 따라 종료; 지급 권리는 생기지 않음 |

| 지급 상태 | 의미 |
| --- | --- |
| 지급 대기 | 성공 권리는 확보됐으나 쿠폰 할당·발급 처리 중 |
| 지급 완료 | 고유 쿠폰 또는 교환권이 해당 사용자에게 귀속됨 |
| 확인 필요 | 공급사 타임아웃 등 결과가 불명확하여 조회·조정 필요 |
| 사용 완료 / 만료 | 발급 후 별도의 사용 상태 |

참여 성공과 지급 작업 생성은 같은 트랜잭션으로 기록한다. 참여당 청구 1개, 쿠폰당 소유권 1개를 DB 고유 제약으로 보장한다. 외부 발급 연동에서는 공급사 주문 키·중복 방지 키·결과 조회를 사용한다. 응답을 잃으면 상태부터 조회하며 새 주문으로 무조건 재발급하지 않는다. 콜백 중복·순서 역전도 처리한다. 외부 시스템까지 무조건 ‘정확히 한 번’이라고 가정하지 않는다.

첫 파일럿은 운영자가 계약·확보한 고유 쿠폰 코드를 안전하게 등록해 할당할 수 있다. 코드는 암호화 보관하고 로그·분석·AI에는 보내지 않는다. 발급 API 공급사가 결정되면 같은 지급 인터페이스 뒤에 연결한다. 공급사에서 사용 여부를 조회할 수 없는 쿠폰은 사용자 수동 표시와 공급사 확인 상태를 구분해 보여준다.

실패한 쿠폰·배송 누락 문의에는 해당 참여와 발급 이력을 연결한다. 운영자 재발급은 사유·권한·기존 쿠폰 처리 결과를 남겨 중복 가치 지급을 막는다.

**5. Q 추천과 학습**

추천은 서버가 먼저 참여 가능한 캠페인을 추리고, 사용자의 희망 혜택·사용 지역·제공 방식·가능한 시간·중복 참여·노출 피로도를 적용한다. 실제 재고와 조건을 통과한 후보만 Q에게 전달한다. Q는 설명과 탐색을 돕고 보상 금액·조건·당첨·재고를 만들어내지 않는다. 후보가 없거나 AI 호출이 실패하면 필터 목록 탐색을 제공한다.

첫 기준은 사용자가 직접 고른 희망 보상이다. 저장된 기억을 브랜드 개인화에 쓰는 것은 일반 교환 학습과 구분해 목적·설정을 설명한다. 사용자가 켜기 전에는 저장된 대화·기억으로 브랜드 타기팅하지 않는다. 광고 참여 이력만으로 ‘좋아한다’를 확정하지 않으며, 학습 설정이 허용할 때 관심 후보를 만들고 사용자의 확인 뒤 저장한다. 동의 철회와 기억 삭제는 대기 중 추천·학습 작업에도 적용한다.

큐의 배지는 ‘첫 브랜드 체험’, ‘새로운 취향 발견’처럼 실제 이벤트에 연결한다. 광고 시청량으로 사용자 간 거래 신뢰 점수나 핵심 매칭 권한을 올리지 않는다. Q는 퍼즐을 대신 풀거나 사용자 대신 광고를 재생·답변하지 않는다. 광고주에게는 집계 결과를 제공하고 개인 채팅·기억·민감한 추론을 내보내지 않는다.

자동 푸시·브랜드 채팅 연락은 별도 허용 범위에서만 실행한다. 첫 버전의 기본 노출은 홈·둘러보기·사용자가 요청한 Q 추천이며 하루 노출·반복 추천 상한을 둔다.

**6. 광고주·운영 기능**

운영 순서는 광고주 등록 → 보상 공급·예산 확인 → 원본·변형 영상과 정답 검수 → 조건·버전 확정 → 공개 → 참여·지급 모니터링 → 결과 보고다. 영상이나 보상 조건 변경은 새 버전으로 발행하며 진행 중 참여에는 시작 당시 버전을 적용한다.

처음에는 운영자가 캠페인을 대신 등록하고 광고주에게 집계 보고서를 제공한다. 광고주 셀프 대시보드는 후속이다. 기존 DavaQ 관리자 권한·감사 기록을 재사용하되, 정답·쿠폰·보상 정정 권한은 운영자 내에서도 구분한다. 이후 광고주 로그인은 별도 조직 멤버십으로 자기 캠페인만 접근하도록 한다.

광고주가 보는 지표: 조건 상세 조회, 참여 시작, 유효 재생 완료, 게임 성공, 재도전, 지급 성공·대기, 혜택 사용 확인, 선택적 브랜드 방문. 30초짜리 영상 두 개 동시 노출을 시청시간 60초로 부풀리지 않는다. 게임 성공·혜택 사용·구매 전환은 별개이며 확인되지 않은 사용·전환은 추정으로 대체하지 않는다.

DavaQ 운영 지표: 지급 중복·미지급·조정 건수, 성공 후 지급 지연, 사용자 이탈·신고·추천 숨김, 실제 보상 원가, 유효 참여당 수익, 첫 일반 교환·재교환으로 이어진 비율. 광고 추천 노출 여부를 나눈 소규모 실험으로 일반 교환 활동을 해치지 않는지도 확인한다.

| 앱 | artifacts/mobile/components/davaq 공통 UI·Tabs·AgentScreens 재사용. 별도 BrandExchangeScreens와 영상 비교 플레이어 추가 |
| 앱 경로 | /brand-exchanges, /brand-exchanges/[id], /brand-exchanges/play/[participationId], /brand-rewards, /brand-rewards/[id] 계획 |
| API | 기존 인증·rate limit·storage·관리자 감사·realtime 재사용. /brand-exchanges 및 /brand-rewards 라우트·서비스 추가 |
| Q | davaqAgent.ts의 실제 후보 조회·설명 흐름 확장. 브랜드 후보와 일반 교환 후보를 명확히 구분 |
| 데이터 | 같은 독립 DavaQ DB에 brand_* 테이블 추가. AnotherMe DB와 사용자 데이터는 참조하지 않음 |
| 작업 처리 | 기존 DavaQ Redis·워커 패턴을 활용하되 보상 원장은 PostgreSQL을 기준으로 함. 발급 작업·예약 만료·조정 작업은 일반 추천 작업과 분리 |
| 계약 | lib/api-spec/openapi.yaml에 계약 정의 후 api-client-react·api-zod 재생성 |

주요 테이블은 브랜드·캠페인·불변 캠페인 버전/소재·보상 풀·고유 보상 재고·참여/시도·참여 이벤트·지급 청구·운영 예산 장부·발급 작업이다. 예: brand_campaigns, brand_campaign_versions, brand_reward_units, brand_participations, brand_attempt_events, brand_reward_claims, brand_budget_ledger, brand_reward_outbox. 분석 집계 데이터와 보상 증빙 기록의 보관 기간은 목적별로 정하며 개인정보 탈퇴 처리와 지급 분쟁 처리도 설계한다.

일반 사용자 간 제안은 양쪽의 동의·이행을 관리한다. 브랜드 교환은 정해진 참여 조건과 지급을 관리하므로, 기존 exchange_proposals의 상태를 억지로 확장하지 않고 별도 상태 모델로 구현한다. 화면의 ‘내 교환’에서는 두 종류를 함께 조회할 수 있다.

API 초안: 캠페인 목록/상세, Q 후보, 참여 시작, 재생·정답 이벤트, 참여 상태/중단/재개/제출, 내 보상 목록/상세/문의, 운영 캠페인 버전·재고·예산·발급 조정. 조건 수정·참여 시작·제출·지급·콜백은 버전과 중복 요청 키를 명시한다.

쿠폰 API·실물 배송은 기존 OpenAI/LiveKit 키로 해결되는 기능이 아니다. 외부 공급사를 연결할 때에는 해당 서비스 계약·자격증명·조회/취소 지원 범위를 추가로 확인한다. 현재 서버에서는 영상 두 개의 송출 부담을 고려해 DavaQ S3와 캐시 가능한 짧은 소재를 사용하고, 트랜스코딩을 웹 요청 처리나 운영 API 프로세스 안에서 실행하지 않는다. 추가 유료 인프라는 부하 측정 후 별도로 산정한다.

**8. 구현 순서와 완료 기준**

아래 기간은 기존 DavaQ를 아는 전담 개발 1명과 디자인·QA 지원, 초기 쿠폰·영상이 준비된 경우의 계획용 추정이다. 첫 파일럿까지 약 5~7주를 예상하며, 쿠폰 계약·소재 제작·최종 특허 대조 및 실기기 발견 사항에 따라 달라진다.

| 순서 | 기간 가정 | 결과와 완료 기준 |
| --- | --- | --- |
| 1. 조건·데이터·화면 설계 | 3~4일 | 캠페인/참여/지급 상태, 약 1분 UX, 보상 재고 정책·권한·API 계약 확정. 테스트용과 실보상 구분 |
| 2. 참여부터 지급까지 연결 | 5~7일 | 운영자 캠페인·재고 등록, 목록·상세·참여 시작·내 혜택. 격리 환경에서 한 번 성공하면 한 보상만 귀속 |
| 3. 두 영상 게임 | 5~7일 | 동기 재생, 정답 판정, 일시 중지·복구, 중복 시도 방지. 실제 iOS/Android 브라우저 확인 |
| 4. 지급 운영 보강 | 4~6일 | 발급 실패·불명확 결과·예약 만료·쿠폰 상태·문의·감사. 사용 가능한 쿠폰 하나의 실제 수령·사용 검증 |
| 5. Q와 기존 화면 통합 | 3~4일 | 희망 보상 추천, 조건 설명, 개인화 설정, 기억 확인, 광고 표시, 노출 빈도·성장 기록 |
| 6. 통합 검증·제한 파일럿 | 5~7일 | 동시성·권한·재접속·실보상 대사, 운영 보고서, 제한 수량 캠페인 배포, 양쪽 서비스 상태 확인 |

이 설계 단계에서 바로 시작할 첫 개발 묶음은 ‘캠페인 상세 → 보상 확보 → 게임 → 지급 → 내 혜택’이다. Q 추천은 참여·지급 경로가 검증된 뒤 연결한다. 화면에 보상 카드를 추가하는 것만으로 출시 완료로 판단하지 않는다.

**9. 반드시 통과할 검증**

- 마지막 쿠폰 한 장에 다수 사용자가 동시에 참여해도 재고·예산이 음수가 되거나 한 코드가 여러 사람에게 배정되지 않는다.
- 새로고침·다중 탭·이벤트 재전송·공급사 콜백 중복·응답 유실에서도 성공 권리와 지급이 일관된다. 발급 결과 불명확 시 새 광고 시청을 요구하지 않는다.
- 미완료 영상·잘못된 시각/좌표·만료 세션·변조 이벤트로 정상 보상을 받지 못하며, 정상 참여의 네트워크 지연에는 복구 유예와 문의 경로가 있다.
- 일시 중지·통화 수신·백그라운드·화면 회전·이어보기 및 320~430px 표시를 검증한다. 소리 없이도 규칙과 정답 피드백을 이해할 수 있다.
- 다른 사용자·다른 광고주·읽기 전용 운영자가 쿠폰·정답·지급 정정에 접근하지 못한다. 사용자 로그아웃 후 코드·푸시가 다른 계정으로 넘어가지 않는다.
- 캠페인 종료·조건 변경·재고 소진이 이미 시작한 유효 참여와 확정 지급 권리를 임의로 없애지 않는다.
- 브랜드 개인화 동의 철회·기억 삭제·학습 미동의를 지키고, Q가 없는 보상이나 조건을 만들지 않는다. 광고 데이터에 들어 있는 지시문은 권한으로 해석하지 않는다.
- 실제 공급사의 쿠폰 발급·수령·사용 상태를 확인하고 장부와 대사한다. 공급사가 없는 모의 테스트를 실제 지급 검증으로 표시하지 않는다.
- 기존 등록·일반 교환·채팅·통화·미디어 접근·PWA 캐시 회귀 검사와 OpenAPI/타입/운영 빌드를 통과한다.

**10. 배포와 다음 확장**

기능 플래그를 분리해 전체 브랜드 교환, 새 참여 시작, Q 추천을 각각 제어한다. 문제 시 신규 노출·참여는 중단하되 이미 성공한 지급과 내 혜택 조회·문의 처리는 계속 가능해야 한다. 전체 API를 끄는 방식으로 보상 채무를 숨기지 않는다.

DavaQ DB 백업·추가형 마이그레이션·테스트 캠페인 → 허용된 파일럿 사용자·소량 실재고 → 지급 대사·기본 교환 활동 확인 → 점진 확대 순으로 배포한다. 같은 서버의 AnotherMe 서비스와 원본 데이터는 변경하지 않는다. 기존 AnotherMe 키 공유 조건을 유지하되 DavaQ AI 호출량과 영상 송출 비용은 별도로 관찰한다.

실물 배송 확장은 배송지 동의·주소 보호·배송 상태·반품/분실·공급자 책임·재고 예약까지 포함한다. 이용권 재교환은 발행자의 양도 허용, 실제 미사용 상태 조회, 양도 시 사용 잠금과 소유권 이전이 가능한 상품부터 허용한다. 일반 쿠폰 이미지를 거래 가능한 자산으로 자동 전환하지 않는다.

특허 구현 대조는 [공개 명세서 KR20220151459A](https://patents.google.com/patent/KR20220151459A/en)의 게임 선택 → 원본/변형 영상 → 성공 판정 → 보상 흐름과, 사용자가 제공한 2026-04-22 결정서를 출발점으로 한다. 공개본 24개와 결정서 22개 청구항 차이가 있으므로 최종 청구항·등록 상태 확인 후 각 구현 요소와 대조표를 만든다. 현재 문서만으로 최종 권리범위나 광고 성과 보장을 주장하지 않는다. 이 확인은 구현 설계와 병행할 수 있으며 현재 코드 작성을 중단해야 한다는 뜻은 아니다.

착수 가정: 첫 공급사는 미정, 초기 운영은 확보한 쿠폰 코드 할당 방식, 광고주는 운영자 대행 등록, 현금화 없음, 캠페인별 확정 보상. 실제 캠페인 공개 전에는 공급 가능한 보상·조건, 허락받은 영상 두 개와 정답, 광고주 비용·예산, 문의/지급 실패 처리 담당을 확정한다.
