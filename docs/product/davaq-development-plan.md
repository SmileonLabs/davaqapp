**1. 제품 방향과 첫 출시 범위**

DavaQ는 사용자가 제공할 수 있는 물건·재능·서비스·경험과 원하는 것을 대화로 등록하고, AI의 도움으로 상대를 찾아 조건에 합의한 뒤 이행까지 관리하는 교환 서비스다. 중심 행동은 “판매하기”가 아니라 “이것을 드리고, 이것을 받고 싶어요”다.

프리미엄 Experience는 초기 공급을 만드는 대표 카테고리다. 윤승현 Experience를 첫 기획전으로 구성하되, 상품·공급자·분류를 데이터로 관리하여 다른 성악가, 촬영자, 디자이너, 경영 멘토도 같은 구조로 참여하게 한다.

첫 버전의 완료 목표는 다음 한 가지다.
“두 사용자가 각자 제공·희망 항목을 등록하고, 실제 후보 추천을 받아 채팅으로 교환을 제안하며, 같은 조건에 동의하고, 약속한 제공을 마친 뒤 서로 완료를 확인한다.”

제공된 시장점유율·경쟁사 이용자 수·경력·권장 가격은 이번 코드 검토로 검증한 사실이 아니다. 시장 기회와 가격은 파일럿에서 검증할 가설로 둔다. 실제 공급자 경력·사진·프로그램 제공 동의를 확인한 뒤 공개한다.

현재 다른 사용자를 대신해 말하는 AnotherMe AI는 교환 계약을 관리하는 중개 엔진과 역할이 다르다. 기존 모델 호출·메시지 전송 기반은 사용하되, 개인 기억이나 관계 데이터를 중개 AI가 자동 열람하지 않도록 별도 문맥과 권한을 둔다.

현재 홈·검색·피드·채팅·미션·마이페이지 구성을 교환 중심으로 바꾼다. 팬·스타·미션·던전·NFT·PVT·지갑 기능은 DavaQ의 초기 사용자 경로와 서버 기능 플래그에서 비활성화한다. 기존 테이블을 급하게 삭제하거나 게임 포인트를 EV로 전환하지 않는다.

**3. 화면과 사용자 흐름**

주요 탭: 홈 / 둘러보기 / 채팅 / 내 교환. 등록은 홈과 둘러보기의 “교환 등록” 버튼으로 제공한다. 채팅 목록 상단에 “DavaQ AI 중개”를 고정한다.

- 홈: 제공할 것·원하는 것 등록, 나에게 맞는 후보, 진행 중 교환, Experience 기획전.
- 둘러보기: 물건 / 재능·서비스 / 경험, 지역·온라인·일정·EV 참고 범위 필터.
- 채팅: AI 등록 도우미, 상대방 대화, 교환 제안 카드, 조건 비교, 확정 버튼.
- 내 교환: 등록 항목, 제안함, 확정 일정, 이행 확인, 후기·신고, 공급자 프로필.
- 운영 화면: 검토 대기, 교환 진행 상태, 신고·분쟁, 정책·경력 검토 이력.

대표 흐름:
1. “발성과 발표 코칭을 90분 제공하고, 브랜드 촬영을 받고 싶어요.”
2. AI가 내용·시간·장소·제공 범위·원하는 교환·가능 일정을 질문한다.
3. 구조화된 등록 초안을 보여준다. 사용자가 수정하고 공개를 누른다.
4. 서버가 조건이 맞는 실제 등록 항목을 찾고, AI가 추천 이유와 미확인 조건을 설명한다.
5. 사용자가 후보에게 제안을 보내면 교환 대화방에서 양쪽 제공 내용이 카드로 표시된다.
6. 일정·장소·준비물·취소 조건을 합의하고, 양쪽이 동일한 제안 버전에 동의한다.
7. 서버가 재고·시간을 다시 확인하여 예약한다. 실제 제공 후 각각 이행 확인과 후기를 남긴다.

공급이 없으면 “현재 맞는 후보가 없음”을 알리고 희망 항목을 저장한다. AI가 없는 상품이나 사용자를 만들어 추천하지 않는다.

**4. Experience 상품 설계**

최초 출시 후보는 기존 10단계안의 4·7·8번으로 한다. 다음 EV는 검증된 시장가가 아니라 공급자와 확인할 초기 제안값이다.

| 프로그램 | 시간 | 초기 희망 EV | 고객이 받는 내용 |
| --- | --- | --- | --- |
| CEO VOICE — Voice, Presence & Leadership | 90분 | 100 | 호흡·발성 30분, 전달력 30분, 발표·IR·연설 연습 30분 |
| Founder / CEO Business Mentoring | 120분 | 300 | 사전 질문을 바탕으로 사업 과제 논의와 실행 과제 정리 |
| Executive Dinner & Mentoring | 180분 | 500 | 사전 의제를 정한 식사·멘토링과 핵심 논의 정리 |

CEO VOICE 등록에는 대상, 진행 방식, 사전 질문, 준비할 발표 자료, 제공 결과물, 장소, 포함·불포함 비용, 일정 변경 조건을 명시한다. 녹음·영상 제출과 통화 녹화는 기본 비활성으로 두고 별도 동의를 받는다.

단순 식사와 멘토링을 포함한 식사는 별도 상품으로 구분한다. 식당 비용이나 장소 대여료를 누가 부담하는지 합의 전에 표시하고, 순수 교환 파일럿에서는 필수 비용까지 공급 패키지에 포함하는 안을 기본으로 검토한다. 프로그램 내용은 투자 성과나 소개·연결을 보장하는 표현으로 작성하지 않는다.

동시에 촬영·디자인·번역·발표 코칭 등 상대적으로 교환 범위를 설명하기 쉬운 공급을 확보한다. 고가 프로그램만 등록하면 서로 원하는 조건이 맞는 상대를 찾기 어렵다. 공급자가 실제 받고 싶은 교환 항목과 가능한 날짜를 함께 확보하는 것이 출시 준비의 일부다.

**5. EV 정의**

초기 표기 가정은 “EV 1 = 1만원 상당을 비교하기 위한 참고 단위”다. 보장된 환율이나 현금 지급 약속이 아니다. 사용자에게는 “희망 교환가치”라는 설명을 붙이고 다음 세 값을 구분한다.

- 공급자 희망 EV: 등록자가 제안한 기준값.
- AI 참고 범위: 근거·기준일·조건·불확실성을 함께 제시할 수 있을 때만 표시.
- 실제 합의 조건: 당사자가 받아들인 제공 항목과 수량·일정. 거래의 기준은 이 합의다.

EV 충전·송금·잔액·현금화·결제·차액 지불은 MVP에 넣지 않는다. 값을 데이터에 기록해 비교할 뿐, EV를 보유하거나 소비하는 지갑을 만들지 않는다. 두 상품의 EV가 같아도 합의가 없으면 교환되지 않고, 달라도 양쪽이 수락하면 교환할 수 있다.

가치 차이는 추가 레슨 회차나 촬영 결과물 등 제공 범위를 바꾸어 협상한다. 첫 버전은 항목을 무한히 조합하기보다 제공 범위가 명확한 패키지 중심으로 운영한다.

“적정도 94%”처럼 검증되지 않은 숫자를 사용자에게 확률이나 공정가격으로 제시하지 않는다. “서로 원하는 분야가 일치”, “온라인 진행 가능”, “희망 날짜 확인 필요”처럼 구체적으로 설명한다. 사진만으로 고가 물품의 진품 여부나 확정 가격을 보장하지 않는다.

**6. AI 중개 기능의 순서**

| 순서 | 기능 | AI 역할 | 서버·사용자 역할 |
| --- | --- | --- | --- |
| 1 | 대화형 등록 | 문장을 항목·조건으로 정리하고 누락 질문 | 스키마 검증, 소유자 공개 확인 |
| 2 | 2자 추천 | 실제 후보를 읽고 이유·차이를 설명 | 지역·일정·유형·재고·차단 관계 필터 |
| 3 | 협상 보조 | 제공 범위 조정안과 합의 초안 생성 | 사용자가 전송·수정·수락 |
| 4 | 이행 지원 | 준비 사항과 진행 상황 요약 | 확정 일정에 따른 알림, 당사자 이행 확인 |
| 5 | 3자 추천 | 서버가 계산한 교환 고리 설명 | 전원 동의, 재고·일정 검증, 예약 |
| 6 | 4자·고도화 | 복잡한 조건의 설명과 대안 | 실패 원인·운영 비용을 확인한 후 확대 |

후보 검색은 모델이 임의 생성하지 않는다. 서버가 조회한 listing ID와 조건만 사용한다. 모델 출력은 구조화된 형식으로 검증하고 권한·상태 검사는 서버가 다시 수행한다.

중개 AI는 공개 등록 정보, 사용자가 중개에 제공한 희망 조건, 참여자에게 공개된 교환 대화만 다룬다. 개인 비공개 희망 조건을 공개하거나 다른 대화방에서 학습한 내용을 상대에게 전달하지 않는다. 중개 계정임을 표시하고 인간 참여자로 가장하지 않는다.

AI는 제안 공개·상대에게 전송·수락·예약 확정·완료·분쟁 해결을 독자적으로 실행하지 않는다. 거래 당사자의 결정과 서버의 거래 규칙이 최종 권한을 갖는다.

**7. 데이터와 API 설계**

기존 DavaQ DB에 교환 도메인 테이블을 신규 추가한다. 아래 명칭은 구현 초안이다.

| 데이터 | 핵심 내용 |
| --- | --- |
| exchange_profiles / provider_verifications | 실제 DavaQ user ID, 소개, 확인한 경력 종류·범위·일자, 확인 상태 |
| exchange_listings / listing_versions | 제공 유형, 상세 범위, 소유자, 수량·시간, 희망 EV, 공개 상태, 버전 |
| exchange_wants | 원하는 항목, 허용 대안, 우선순위, 지역·온라인·일정 제약, 공개 범위 |
| exchange_availability | 가능한 시간대·정원·재고, 유효기간 |
| exchange_proposals / proposal_versions | 제안자, 방 ID, 만료 시각, 조건 버전, 변경 이력 |
| exchange_legs / proposal_acceptances | 누가 누구에게 무엇을 제공하는지, 버전별 명시적 동의 |
| exchanges / exchange_reservations | 확정 합의 스냅샷, 상태, 예약 자원과 만료·해제 |
| exchange_fulfillments / exchange_reviews | 제공별 증빙·수령 확인, 완료 교환의 당사자 후기 |
| exchange_disputes / category_policies | 신고·조정·처리 이력, 허용·검토·제한 카테고리 |
| exchange_outbox / matching_jobs | 상태 변경 이후 알림·검색 동기화·추천 작업의 재시도 |

제안 버전을 양쪽이 수락하면 서버가 단일 트랜잭션 안에서 최신 조건과 자원을 검증하고 확정 합의·예약을 생성한다. 확정된 제공 범위는 원래 상품이 수정되어도 변하지 않는다.

확정 이후 조건 변경은 새 변경안과 전원 재동의가 필요하다. 공개 상품 삭제, 채팅 숨김·메시지 삭제가 기존 합의·분쟁 증거를 지우지 않도록 보존·열람 정책을 별도로 설계한다.

API 예:
- GET/POST /exchange/listings, PATCH /exchange/listings/:id, POST .../:id/publish
- GET/POST /exchange/wants, GET /exchange/matches
- POST /exchange/proposals, POST .../:id/revisions
- POST /exchange/proposals/:id/accept — proposalVersion과 멱등성 키 필수
- GET /exchanges/:id, POST .../:id/change-requests, POST .../:id/cancel
- POST /exchanges/:id/fulfillments, POST /exchanges/:id/confirm-receipt
- POST /exchanges/:id/disputes, POST /exchanges/:id/reviews
- POST /exchange/assistant — 초안·질문·추천 설명; 거래 결정은 전용 API 경유

OpenAPI 원본을 수정한 뒤 기존 생성 절차로 클라이언트와 검증 스키마를 갱신한다. 생성 파일을 직접 편집하지 않는다.

**8. 거래 상태와 실패 처리**

등록: 초안 → 검토 필요 또는 공개 → 예약됨/일시중지 → 종료.
제안: 작성 → 전달 → 협상 → 동일 버전 전원 동의 → 확정, 또는 거절/철회/만료.
교환: 예약 → 일정 확정 → 이행 중 → 제공별 수령 확인 → 전체 완료.
취소 요청·분쟁은 현재 이행 상태와 연결하여 별도 처리한다.

구현 필수 조건:
- 상품 한 개나 같은 강사의 같은 시간을 동시에 두 교환에 확정할 수 없어야 한다.
- 버튼 중복 클릭·네트워크 재전송이 중복 수락·중복 예약을 만들지 않아야 한다.
- 조건 수정 시 이전 버전 동의로 확정하지 않아야 한다.
- 확정 전 제안은 자유롭게 거절·철회할 수 있고, 임시 보류는 기한 후 풀려야 한다.
- 확정 후 취소는 합의된 조건과 진행 상태를 따른다. 일부 서비스가 제공되었다면 전체 미이행처럼 처리하지 않는다.
- 물건 배송, 촬영 결과물 전달, 레슨 참석 등 유형별 제공·수령 확인을 기록한다.
- 한 사람의 완료 클릭만으로 전체 교환을 자동 완료하거나 후기를 조작할 수 없어야 한다.
- 분쟁 중 자동 완료를 중단하고 운영자가 증거·합의 조건을 보고 조정할 수 있어야 한다.
- 계정 차단 이후에도 이미 확정한 교환은 필요한 범위의 연락·취소·신고 경로가 있어야 한다.

플랫폼의 예약 트랜잭션은 이중 예약을 막을 수 있지만, 오프라인 물건과 경험의 동시 이행을 보장하지는 못한다. 에스크로를 구현하지 않은 상태에서 보호·보상을 보장하는 UI를 사용하지 않는다.

**9. 3·4자 교환 설계**

먼저 실제 2자 교환을 운영하고, “원하는 상대는 있지만 역방향 수요가 맞지 않아 실패한 제안”이 누적될 때 3자를 추가한다.

예시:
- A: 성악 레슨 제공 / 사진 촬영 희망
- B: 사진 촬영 제공 / 골프 레슨 희망
- C: 골프 레슨 제공 / 성악 레슨 희망
- 실제 제공 방향: A → C(성악), C → B(골프), B → A(촬영)

사용자 수만으로 교환 고리를 만들지 않는다. 제공 항목·희망 조건·재고·시간의 연결을 계산하고 서로 다른 참여자, 가능한 일정, 이동 범위, 차단 관계, 정책 제한을 검증한다.

3자 제안에는 각자가 주고받을 것, 순서, 예약 기한, 취소 조건을 함께 표시한다. 제한 시간 동안 자원을 보류하고 전원 동의 시 DB에서 예약을 확정한다. 한 명이 거절하거나 만료되면 해당 제안을 종료하고 보류를 해제한다. 이미 일부 이행한 이후의 이탈은 제안 취소가 아니라 분쟁·부분 이행 처리다.

PostgreSQL이 거래·재고·동의의 원본이다. 초기 2자 추천은 PostgreSQL 질의와 규칙으로 시작한다. 필요할 때 DavaQ Neo4j에 별도 교환 그래프를 만들고 outbox로 동기화한다. 그래프는 후보 탐색용이며, 오래된 후보를 확정하기 전에 PostgreSQL에서 다시 검증한다. 기존 개인 지식 그래프 노드를 교환 그래프에 무단 연결하지 않는다.

4자는 3자에서 전원 수락률·완료율·취소율·운영 부담이 확인된 후 진행한다. 길이가 제한된 탐색과 비동기 작업을 사용하고, 현재 공유 서버에서 무제한 전체 그래프 탐색을 실행하지 않는다.

**10. 신뢰·카테고리 정책과 운영**

파일럿은 검토한 성인 공급자와 제공 범위가 명확한 카테고리로 한정하는 안을 제안한다. 초기 온라인 서비스·Experience와 선택한 지역의 직접 교환부터 시작하고, 고가 물품 배송·복잡한 보관·진품 감정은 이후 범위로 둔다.

- 경력 확인은 “본인 확인”, “경력 자료 확인”, “자격 확인”을 구분하여 표시한다. 확인하지 않은 역량까지 인증한 것처럼 표시하지 않는다.
- 후기 작성은 실제 교환 참여자에게만 허용한다. 캐릭터를 바꾸어도 user ID에 연결된 평판이 유지된다.
- 제한 카테고리는 검색만 숨기는 방식이 아니라 등록·제안·매칭·확정 단계에서 서버가 차단한다.
- 이용권은 양도 가능 여부·유효기간·발행처 조건을 확인한 후 허용한다.
- 주류 및 의료·법률·투자 관련 전문서비스는 실제 운영 형태별 검토와 필요한 공급자 자격 확인 전에는 초기 자동 등록·추천 대상에서 제외하는 안을 권고한다.
- 사업 경험 공유와 개별 투자 권유 등은 등록 범위·안내·검토 기준을 분리하여 검토한다.
- 비공개 주소·연락처·증빙은 필요한 당사자와 권한 있는 운영자만 열람하도록 한다. AI에는 필요한 최소 정보만 전달한다.
- 이용약관·개인정보·취소·분쟁·거래기록 보존·세무 처리 범위는 출시 전에 운영 주체와 검토하고 제품 상태 모델에 반영한다.

주류에는 별도의 통신판매 고시가 존재하며, 국세청 질의회신도 플랫폼의 주류 중개 여부를 계약관계·책임 부담 등에 따른 사실판단 사항으로 설명한다. 따라서 EV 또는 물물교환 명칭만으로 허용된다고 가정하지 않는 개발 정책이다. 여기서 개별 서비스의 적법성을 확정한 것은 아니다.
공식 참고: [주류 통신판매 고시](https://www.law.go.kr/행정규칙/주류의통신판매에관한명령위임고시), [국세청 질의회신](https://taxlaw.nts.go.kr/qt/USEQTA002P.do?ntstDcmId=200000000000002942).

**11. 구현 위치와 서비스 분리**

- artifacts/mobile/app/(tabs): 교환 탭·온보딩 구성.
- artifacts/mobile의 교환 화면·컴포넌트: 등록, 상품, 제안 비교, 합의, 일정, 이행, 후기.
- artifacts/api-server/src/routes: exchangeListings, exchangeProposals, exchanges, exchangeAssistant, exchangeAdmin 모듈 신규 구성.
- artifacts/api-server/src/lib: 거래 상태 전이, 추천 규칙, 예약, 중개 도구, 정책 검증을 UI와 분리.
- lib/db/src/schema 및 migrations: 교환 도메인과 제약·인덱스 추가.
- lib/api-spec: 공개 계약 정의 후 API 클라이언트·검증 코드 생성.
- artifacts/landing: 메신저 기반 교환 설명, 실제 공급자의 Experience와 앱 진입 경로.
- docs/operations: 백업·배포·복구, AI 사용량, 매칭 작업, 분쟁 운영 절차.

AnotherMe 소스·DB·파일·개인 기억을 읽어오는 방식으로 확장하지 않는다. 같은 Clerk ID라도 DavaQ의 사용자 행과 교환 프로필을 사용한다. OpenAI·LiveKit 키 재사용은 유지할 수 있지만 사용량·요금·외부 서비스 장애는 공유되므로 DavaQ별 요청 제한과 비용 측정을 둔다.

기존 배포 기록상 공용 Caddy 라우팅을 AnotherMe 배포가 덮어쓰지 않게 보존해야 한다. 초기 개발 단계에서 공용 라우팅 관리와 DavaQ 배포 점검을 명시한다. DB 변경은 DavaQ 백업·복구 확인 후 전진 마이그레이션으로 적용하고, 앱 기능 플래그와 이전 이미지로 단계별 복구가 가능하게 한다.

첫 출시는 현재 PWA 기준이다. 네이티브 앱스토어 출시는 별도 EAS·Firebase 설정과 심사를 포함하는 후속 일정으로 분리한다. 출시 전 실제 두 계정 로그인, 양방향 채팅·알림, 두 사용자 통화를 검증한다.

**12. 단계별 실행 계획**

전담 개발 2명과 비상근 디자인·QA, 공급자 확보와 검토를 담당할 운영 인력을 가정한 6~8주 MVP 계획용 추정이다. 실제 일정은 레거시 권한·화면 의존성 점검과 공급자·운영정책 준비 결과에 따라 조정한다. 3·4자 교환, 앱스토어 출시, AI 감정 서비스는 이 일정에 포함하지 않는다.

| 단계 | 기간 가정 | 산출물 | 통과 조건 |
| --- | --- | --- | --- |
| A. 제품 전환·도메인 설계 | 1주 | DavaQ 화면, 공급자·등록·희망 모델, EV 정의, 운영정책 초안 | 원래 게임 흐름 없이 가입→등록 초안까지 진행 |
| B. 2자 교환 기반 | 2주 | 상품·제안·버전 동의·예약·일정·완료·취소·신고 | 두 계정이 수동 검색부터 전체 교환 흐름 완료 |
| C. AI 중개와 Experience | 1~2주 | 대화 등록, 규칙 기반 후보와 설명, 대표 3상품 템플릿, 교환 카드 | 실제 후보만 제안하고 사람의 동의 없이 확정하지 않음 |
| D. 출시 검증·초대 파일럿 | 2~3주 | 운영 화면, 핵심 오류 대응, 실제 교환, 측정 대시보드 | 권한·동시성·이행 검증 통과, 공급자·상대 수요 확보 |

후속: 파일럿의 매칭 실패 이유를 분석한 뒤 3자 교환을 별도 견적·일정으로 설계한다. 4자 교환과 자동 가치 추정 고도화는 그 다음이다.

MVP 제외: EV 지갑·코인, 현금 결제·차액 결제, 자동 계약 수락, 투자 상품 거래, 무검증 주류 등록, 거래 이행 보장, 전체 AnotherMe 대화 기반 추천.

수익모델은 별도 제품 의사결정으로 남긴다. 향후 공급자 도구 구독이나 운영 대행을 검토할 수 있지만, MVP에는 결제 기능을 넣지 않는다. “현금 없는 교환”과 플랫폼 이용료 정책은 출시 안내 전에 구분하여 결정한다.

**13. 검증과 성공 기준**

출시 전 필수 시나리오:
1. 동일 수량·동일 시간에 동시 수락해도 하나만 예약된다.
2. 구버전 수락, 요청 재전송, 동의 직전 조건 수정이 잘못된 확정을 만들지 않는다.
3. 교환에 참여하지 않은 계정이 합의·주소·증빙·대화·상태 변경에 접근하지 못한다.
4. 공개 중단·계정 제한·차단·만료·낡은 추천 결과가 확정 전에 재검증된다.
5. 한쪽만 제공, 노쇼, 취소 요청, 분쟁이 전체 완료로 잘못 집계되지 않는다.
6. AI에 상품 설명으로 명령을 넣어도 비공개 정보 열람이나 자동 수락이 실행되지 않는다.
7. 필수 AI 출력 누락·외부 API 실패 때도 수동 등록·검색·제안이 가능하다.
8. 서비스 분리, 파일 접근 권한, 알림 수신자, 실제 로그인·통화·PWA 동작을 확인한다.

핵심 성과는 실제 완료한 교환과 다시 교환한 사용자다. 총 희망 EV나 AI 추천 점수를 거래 성과로 집계하지 않는다.

| 지표 | 정의·용도 |
| --- | --- |
| 등록 완료율 | 공개 가능한 제공·희망 조건을 저장한 사용자 / 등록 시작 사용자 |
| 유효 후보 확보율 | 운영상 정한 기간 내 필수 조건을 충족한 후보가 있는 요청 / 추천 요청 |
| 제안 전원 수락률 | 전원이 같은 버전에 동의한 제안 / 전달된 제안 |
| 교환 완료율 | 관찰 기한이 도래한 확정 교환 중 모든 제공을 확인한 교환 비율 |
| 이행 위험 | 취소·노쇼·분쟁을 별도로 집계하고 제공 유형별 비교 |
| 첫 완료까지 시간 | 첫 등록부터 첫 교환 완료까지 걸린 시간 |
| 반복 교환 | 첫 완료 후 30일 관찰이 끝난 사용자 중 추가 교환 완료 비율 |
