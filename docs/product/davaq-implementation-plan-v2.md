# DavaQ 구현 계획 v2 — 확정 시안 9개 기준
작성일: 2026-09-12
상태: 2026-09-12 첫 PWA MVP 구현·배포. 실제 구현과 검증 범위는 [릴리스 기록](../operations/davaq-exchange-mvp-20260912.md)을 기준으로 확인한다. 아래 일정은 착수 당시 계획이며 파일럿 검증 항목은 별도로 남긴다.
코드 검토 기준: 독립 DavaQ 저장소 main 264006d.
디자인 기준: docs/design/2026-09-12-mobile-v1의 최종 PNG 3장.

**1. 이번 계획에서 확정하는 범위**

제품은 “내가 제공할 것과 원하는 것을 말하면, 나를 이해하는 AI가 실제 후보를 찾고 채팅에서 교환 합의를 돕는 서비스”다. 승인된 시안의 밝은 화면, 보라색 브랜드, 큐 캐릭터, 5개 메뉴와 9개 대표 화면을 구현 기준으로 삼는다.

이 문서는 기존 davaq-development-plan.md와 davaq-agent-growth-plan.md의 화면 구성·우선순위·출시 범위·일정 추정을 통합하여 대체한다. 앞선 4개 탭안 대신 5개 탭안을 적용한다. 초기 사업 가설과 가격 템플릿의 배경은 기존 문서에 남긴다.

첫 출시는 현재 도메인의 모바일 PWA다. 같은 EC2에서 독립 DavaQ 소스·DB·Redis·Neo4j·파일 저장소를 사용하고, Clerk 로그인과 승인된 외부 API 키 재사용 조건을 유지한다. AnotherMe의 대화·프로필·기억은 가져오지 않는다.

**2. 화면 구조**

하단 탭 순서: 홈 / 둘러보기 / 채팅 / 내 AI / 내 교환.

| 화면 번호 | 시안 | 역할 | 진입·다음 행동 |
| --- | --- | --- | --- |
| 01 | 홈 | 등록과 새로운 교환 기회의 시작점 | 제공/희망 등록, 추천 상세, 오늘 가능한 항목 |
| 02 | 둘러보기 | 물건·재능·경험 탐색 | 필터·검색·관심 저장, 상품 상세, 등록 |
| 03 | 내 AI | 큐의 성장·기억·탐색 관리 | 기억 관리, 학습 설정, 추천 확인 |
| 04 | 채팅 | AI와 상대방 대화 목록 | 개인 큐 대화, 교환방, 진행 상태별 필터 |
| 05 | 교환 협상 | 대화에서 조건을 정리하고 동의 | 제안 버전 비교, 제공별 일정, 조건 확인 |
| 06 | 내 교환 | 제안·예약·등록·완료 관리 | 교환방, 이행 확인, 등록 수정, 재교환 |
| 07 | AI와 교환 등록 | 말로 시작해 구조화된 항목 공개 | 초안 수정·저장·공개 |
| 08 | Experience 상세 | 제공 범위와 원하는 교환 이해 | 제공자 소개, 일정·조건, 내 항목으로 제안 |
| 09 | AI 매칭 추천 | 실제 후보와 선정 이유 확인 | 제안 초안, 부정 피드백, 다른 후보 |

01·02·03·04·06은 하단 탭을 유지한다. 05는 메시지 입력창, 07·08·09는 해당 화면의 주요 행동 버튼을 하단에 둔다. 뒤로 가면 탐색 필터·스크롤·작성 중 내용을 가능한 범위에서 유지한다.

개인 프로필과 일반 설정은 내 교환 상단에서 진입한다. 내 AI의 설정 버튼은 학습·말투·알림 범위로 연결한다. 교환 일기는 별도 탭 대신 홈의 경험 영역에서 확장한다.

권장 라우트 초안:
- 기존 (tabs)/index, (tabs)/search, (tabs)/chats를 홈·둘러보기·채팅으로 전환.
- (tabs)/agent, (tabs)/exchanges 신규 추가.
- 기존 chat/[id]의 메시지 기능을 보존하며 교환방 유형을 확장.
- exchange/new, exchange/listings/[id], exchange/matches/[id], exchange/proposals/[id], exchange/deals/[id] 신규 구성.
- agent/memories, agent/settings, agent/searches 신규 구성.
- 기존 persona·settings/ai-memories 등 링크는 역할에 맞게 전환·연결하고 폐기한 화면으로 진입하지 않도록 한다.

실제 Expo Router 파일 배치는 충돌과 기존 깊은 링크를 확인한 후 고정한다.

**3. 디자인을 실제 컴포넌트로 옮기는 작업**

시안 이미지를 화면 전체 배경으로 붙이지 않는다. 제목·버튼·목록·카드는 React Native 컴포넌트로 만들고 실제 데이터·접근성·상태 처리를 연결한다.

- 색: 주요 보라색 #6D4AFF, 밝은 배경 #F7F6FB, 흰 카드, 짙은 본문 #242438을 시작값으로 사용한다. 실제 대비와 선택·비활성 상태를 검증해 토큰을 고정한다.
- 현재 (tabs)/_layout.tsx의 강제 dark ThemeModeContext와 neon 배경을 제거하고 DavaQ 공통 테마를 적용한다. 기존 글자·입력창이 섞여 보이지 않도록 로그인·설정·시트·채팅까지 점검한다.
- 첫 출시는 시안의 라이트 모드를 기준으로 한다. 다크 모드의 별도 디자인 검증은 후속 범위로 두며 시스템 다크 설정에서도 읽기 가능한 상태를 보장한다.
- 한글 글꼴은 적법하게 배포 가능한 실제 폰트 또는 플랫폼 기본 글꼴을 정하고 크기·굵기·행간을 통일한다.
- 기준 모바일 폭 390px, 320/360/430px와 태블릿·데스크톱 폭에서 확인한다. PWA 하단 안전 영역·키보드·브라우저 뒤로가기를 처리한다.
- 버튼 터치 영역, 긴 제목 줄바꿈, 아이콘 설명, 글자 확대, 스크린리더 레이블을 포함한다.
- 큐는 시안과 같은 외형의 독립 이미지 자산으로 제작한다. 첫 단계는 기본/탐색/발견/확인 대기/교환 완료 포즈와 카메라 등 관심 장식이다. 화면 이미지에서 글자와 함께 잘라 쓰지 않는다.
- 첫 버전의 큐는 가벼운 이미지와 상태 전환 애니메이션으로 구현한다. 실시간 3D 엔진과 무한 자동 움직임은 필요할 때 별도 검토한다.
- 경험·물품 사진과 공급자 사진은 실제 공개 가능한 자산을 연결한다. 시안 속 가상 인물·거래·일정을 운영 데이터로 넣지 않는다.

공통 컴포넌트 초안:
DavaQScreen, DavaQTabBar, Header, PrimaryButton, FilterChip, ListingCard, ExchangePairCard, AgentAvatar, AgentBubble, MemoryCard, ProposalCard, ExchangeStatusBadge, ScheduleRow, EmptyState, ErrorState, LoadingSkeleton.

교환 카드의 공통 데이터는 “내가 제공하는 것 / 내가 받을 것 / 상대 / 조건 버전 / 상태 / 다음 행동”으로 맞춘다. 보는 사람의 user ID에 따라 주고받는 방향을 계산한다.

**4. 9개 화면의 상세 구현과 완료 조건**

| 화면 | 첫 출시 필수 구현 | 완료 조건 |
| --- | --- | --- |
| 01 홈 | 큐의 실제 새 추천, 제공/희망 버튼, 추천 교환, 오늘·온라인 필터 카드 | 모든 행동이 실제 등록·상세·채팅으로 연결되고 없는 후보 수를 만들지 않음 |
| 02 둘러보기 | 키워드·카테고리·지역/온라인·일정 필터, 관심 저장, 페이지 추가 로딩, 등록 | 공개 중인 항목만 검색되며 종료·품절 상태가 상세/제안에서 재검증됨 |
| 03 내 AI | 이름·기본 외형, 성장 이정표, 근거 있는 기억, 설정, 실제 탐색 기록 | 기억 확인/수정/삭제가 다음 추천에 반영되고 미동의 대화는 수집되지 않음 |
| 04 채팅 | 내 큐 대화 상단 배치, 전체/제안/진행 중 필터, 미읽음, 교환 상태 | 재접속·재전송·읽음 처리가 유지되며 상태와 상대방 권한이 일치함 |
| 05 교환 협상 | 일반 메시지, AI 요약 초안, 제안 버전, 제공별 일정, 명시적 동의 | 구버전 수락·동시 수락·중복 요청이 잘못된 확정이나 이중 예약을 만들지 않음 |
| 06 내 교환 | 진행 중/내 등록/완료, 받은 제안, 일정, 등록 관리, 제공별 이행·수령 확인, 재제안 | 한쪽 제공만 완료된 교환을 전체 완료로 표시하지 않으며 취소/분쟁 경로가 있음 |
| 07 AI 등록 | 대화 입력, 질문, 구조화된 초안, 수동 수정, 사진, 임시 저장, 공개 | 내가 확인한 내용만 공개되고 AI 실패 때 수동 등록이 가능함 |
| 08 Experience 상세 | 실제 공급자, 제공 내용, 시간·정원·일정, 희망 항목, 참고 EV, 포함/취소 조건 | 공급자가 확인한 조건을 읽고 내 제공 항목을 골라 제안할 수 있음 |
| 09 AI 추천 | 실제 후보, 주고받는 항목, 근거·미확인 조건, 피드백, 제안 초안 | 존재하는 항목만 추천하며 거절 사유가 잘못 일반화되지 않고 전송은 내 확인 후 수행 |

홈의 “줄 수 있어요”는 제공 등록으로, “받고 싶어요”는 희망 등록으로 시작한다. 희망 항목만 먼저 저장하는 것도 허용한다. 교환 제안 시에는 상대가 받을 수 있는 내 제공 항목을 선택하거나 새로 등록한다.

“오늘 30분”은 별도 거래 시스템이 아니라 소요 시간·온라인 여부·가능 시간으로 필터한 동일한 상품·제안 흐름이다. 관심 저장과 위시리스트도 같은 제공·희망 데이터에 연결한다.

둘러보기의 “내 주변”은 사용자가 선택한 활동 지역을 기본으로 하고, 위치 권한은 필요할 때 요청한다. GPS 권한 거절 시에도 지역 선택으로 사용할 수 있어야 한다.

**5. 시안 외에 함께 구현해야 하는 화면·상태**

9개 시안은 대표 화면이며 다음 보조 흐름까지 포함해야 실제 서비스가 된다.

- 로그인 후 최소 온보딩: DavaQ 프로필, 활동 지역/온라인 여부, 첫 제공 또는 희망, 큐 기본 설정.
- 내 등록 상세·수정·일시중지·삭제와 이미지 업로드 진행/실패.
- 제안 작성·수정·거절·철회, 조건 비교, 버전별 동의 상태.
- 확정 교환 상세: 양쪽 제공 범위, 서로 다른 제공 일정, 장소·준비물·연락 경로.
- 제공 완료 알림과 상대방 수령 확인, 전체 완료 후 후기, 다음 교환 제안.
- 일정 변경 요청, 취소 요청, 노쇼·부분 이행·분쟁·신고.
- 기억 목록·출처·확인·수정·삭제, 학습 범위·알림·탐색 설정.
- 공급자 소개와 경력 검토 상태, 신고·차단, 운영자 검토·처리 기록.
- 알림함과 해당 제안/교환/기억 카드로 이동하는 깊은 링크.

각 대표·보조 화면에 로딩, 빈 상태, 오류/재시도, 권한 없음, 삭제/만료, 연결 끊김을 포함한다. 필수 미확인 항목이 있으면 확정 버튼을 활성화하지 않고 해당 입력으로 연결한다. 데모 데이터는 개발·검토용 환경에만 두고 운영 화면에는 분리된 실제 데이터를 사용한다.

**6. 교환 데이터와 상태 모델**

새 데이터는 DavaQ에만 저장한다. PostgreSQL을 거래·예약·동의·기억 권한의 원본으로 사용한다. Redis는 작업·캐시, Neo4j는 필요할 때 후보 탐색용 파생 그래프로 사용한다.

| 도메인 | 주요 테이블 초안 | 용도 |
| --- | --- | --- |
| 공급자 | exchange_profiles, provider_verifications | 계정 기준 프로필·확인 범위 |
| 제공·희망 | exchange_listings, listing_versions, exchange_wants, listing_favorites | 유형·상태·조건·관심 저장 |
| 자원 | exchange_availability, exchange_reservations | 수량·시간·정원·예약 |
| 제안 | exchange_proposals, proposal_versions, proposal_acceptances | 조건 변경과 같은 버전에 대한 동의 |
| 실제 교환 | exchanges, exchange_legs, exchange_fulfillments | 누가 누구에게 무엇을 언제 제공하는지·수령 확인 |
| 사후 관리 | exchange_reviews, exchange_disputes, exchange_events | 후기·분쟁·변경 이력 |
| 개인 AI | agent_learning_settings, agent_memories, agent_growth_events | 동의·근거·기억·성장 |
| 탐색 | agent_search_missions, agent_search_runs, agent_match_feedback, exchange_outbox | 탐색 범위·실행 기록·피드백·재시도 |

기억 후보와 확인된 기억은 동일 테이블의 명확한 상태로 구현하거나 별도 테이블로 나눌 수 있다. 핵심은 원문·근거·확인 상태·유효기간·공개 범위·삭제 상태를 추적하는 것이다.

상품: 초안 → 검토/공개 → 예약/일시중지 → 종료.
제안: 작성 → 전달 → 협상 → 동일 버전 전원 동의 → 확정, 또는 거절/철회/만료.
교환: 예약 → 일정 확정 → 제공별 이행·수령 확인 → 전체 완료. 취소·분쟁은 진행 상태에 연결한 별도 전이로 처리.

확정 시 제공 범위와 일정의 스냅샷을 저장한다. 이후 상품 수정이 확정된 조건을 바꾸지 못한다. 서비스 시간이 서로 다를 수 있으므로 각 제공 항목에 독립 일정을 둔다. 같은 소유자의 동일 시간이나 물품 수량을 두 교환에 동시에 예약하지 못하게 한다.

조건 수정 시 이전 버전 동의는 새 버전에 적용하지 않는다. 양쪽 동의가 모이면 트랜잭션으로 최신 항목·권한·상태·재고·시간을 검증하고 예약한다. 멱등성 키와 DB 제약으로 중복 실행을 막는다.

교환 완료와 후기 권한은 실제 계정과 거래 참여를 기준으로 한다. 캐릭터 변경·방 숨김·메시지 삭제가 평판이나 합의 이력을 우회하는 경로가 되어서는 안 된다.

**7. API와 기존 코드 연결**

기존 Express·Drizzle·OpenAPI·React Query 구조를 유지한다. API 원본은 lib/api-spec/openapi.yaml이며 클라이언트와 Zod 생성물은 기존 codegen으로 갱신한다.

주요 API 그룹:
- /exchange/home: 홈 추천·진행 항목·오늘 가능한 공급의 제한된 요약.
- /exchange/listings, /exchange/wants, /exchange/favorites: 등록·검색·공개·관심.
- /exchange/matches: 실제 후보·추천 이유·미확인 조건.
- /exchange/proposals: 생성·수정·버전 동의·거절·철회.
- /exchanges: 확정 내용·일정 변경·제공/수령 확인·취소·후기·분쟁.
- /agents/me: 프로필·꾸미기·성장 이벤트.
- /agents/me/memories, /agents/me/learning: 기억과 학습 제어.
- /agents/me/searches, /agents/me/matches/feedback: 탐색 설정·실행 상태·피드백.
- /admin/exchange: 등록·경력·정책·분쟁 검토. 별도 역할과 감사 기록.

기존 rooms/messages/realtime/calls/storage/blocked의 인증과 접근 검사를 재사용하고 새 객체의 소유·참여 권한 검사를 추가한다. 채팅 UI는 기존 전송 outbox, 순서 번호, 중복 방지, 읽음·재연결 훅을 유지한다. 메시지 metadata에는 제안 참조·버전 등만 넣고, 실제 수락 여부는 거래 테이블에서 읽는다.

우선 수정 위치:
- artifacts/mobile/app/(tabs)/_layout.tsx, app/_layout.tsx, onboarding.tsx
- artifacts/mobile/constants/colors.ts, hooks/useColors.ts, hooks/useThemeMode.tsx
- artifacts/mobile/components/ChatsScreenV2.tsx 및 components/chat, app/chat/[id].tsx
- artifacts/mobile의 신규 exchange/agent 화면·컴포넌트·hooks
- artifacts/api-server/src/routes의 신규 교환·개인 AI 경로 및 관련 lib 서비스
- lib/db/src/schema, lib/db/drizzle, lib/api-spec/openapi.yaml
- artifacts/landing의 앱 설명·실제 Experience 진입 링크

기존 게임·팬/스타·미션·NFT·지갑 진입을 DavaQ 내비게이션·온보딩·서버 기능에서 비활성화한다. 공통 계정·대화와 얽힌 테이블을 일괄 삭제하지 않고 의존성을 확인하며 단계적으로 정리한다.

**8. 첫 출시의 AI 범위**

첫 출시에도 ‘내 AI’는 실제 동작해야 한다.

1. 사용자가 확인한 제공·희망·가능 조건과 명시적 말투 설정을 기억한다.
2. 관심 저장·추천 거절 이유·교환 후기를 개인화 신호로 사용한다. 약한 추정은 확인 전 상태로 둔다.
3. 대화 학습을 따로 켠 경우 선택한 DavaQ 대화의 내 발화에서 교환 관련 기억 후보를 추출한다. 과거 모든 대화의 일괄 수집은 하지 않는다.
4. 사용자가 확인·수정·삭제할 수 있고 변경이 이후 질문·추천·표현에 반영된다.
5. 첫 등록·취향 확인·첫 완료·재교환 같은 실제 이벤트로 성장과 외형을 바꾼다. 채팅 도배나 접속 일수만으로 성능이 늘었다고 표현하지 않는다.
6. 사용자가 켜둔 탐색 요청에 대해 신규 상품·선호·일정 변경 시 제한된 비동기 탐색을 수행한다.
7. 탐색 상태와 추천 이유를 보여주고, 실제 후보가 없으면 없다고 표시한다.

매칭의 하드 조건은 공개 상태·제공/희망의 양방향 적합성·지역·일정·재고·정책·차단이다. 그 뒤 개인화 조건으로 정렬한다. AI는 실제 후보의 의미 정리와 설명·질문·협상 초안을 담당한다.

개인 큐의 비공개 기억과 공통 매칭 서버·교환방 중개 문맥을 분리한다. 에이전트 간 공유는 사용자가 매칭에 허용한 구조화된 제공·희망 조건으로 제한한다. 원문 대화나 개인 협상 한계를 서로 전달하지 않는다.

성장 레벨은 꾸미기와 여정 표시다. 사용자 권한·교환 수락·상대 연락 권한과 연결하지 않는다. 제안 전송·제공 범위 변경·예약 확정은 명시적 확인을 거친다.

삭제는 DB 상태뿐 아니라 캐시·파생 그래프·진행 중 작업의 사용 가능 여부에 반영한다. 저장된 동의 버전을 작업 실행·결과 적용 시 다시 검사하여 동의 철회 후 뒤늦게 학습 결과가 저장되지 않게 한다.

기존 키를 공유하므로 DavaQ별 호출 한도·비용·실행 시간·재시도 상한을 둔다. 매 메시지마다 모델을 재훈련하거나 모든 에이전트를 서로 장시간 대화시키는 구조로 시작하지 않는다.

**9. 첫 출시와 후속 기능의 구분**

| 첫 출시 | 후속 확장 |
| --- | --- |
| 9개 대표 화면 + 필수 보조 흐름 | 교환 이야기 공개 피드·공유 카드 |
| 물건·재능·경험의 2자 교환 | 주제별 교환 모임·기획전 운영 도구 |
| 짧은 교환, 관심 저장, 수동 재제안 | 반복 일정 템플릿·교환 짝꿍 |
| 대표 Experience 3개를 담을 수 있는 데이터 구조 | 나머지 10단계 상품 확장과 그룹 Experience |
| 큐 외형·기억·피드백 기반 추천·실제 탐색 기록 | 더 풍부한 외형·표현과 위임 조건 문의 |
| 선택한 내 대화의 동의 기반 기억 후보 | 더 넓은 학습 범위는 별도 동의·검증 후 |
| 새 공급·조건 변화에 따른 제한된 자동 탐색 | 3자 교환, 이후 4자 교환 |
| 모바일 PWA | 새 EAS·Firebase 설정 및 앱스토어 배포 |

첫 출시에는 결제·EV 충전/잔액·현금화·차액 결제·AI 단독 확정을 넣지 않는다. EV는 공급자가 입력한 참고 교환가치다. 시안의 EV100은 운영 공급자가 확인할 초안이며 고정된 시장가로 취급하지 않는다.

출시 카테고리는 운영자가 검토한 범위로 한정한다. 주류·자격이 필요한 전문서비스·양도 제한 이용권은 기존 정책 설계에 따라 검토 전 자동 등록·매칭을 제한한다. 구체적 법률·세무 결론을 이 구현 문서에서 확정하지 않는다.

**10. 실행 단계와 예상 일정**

전담 개발 2명, 비상근 디자인·QA 및 공급자·검토·분쟁을 담당할 운영 인력을 가정한 8~10주 계획용 추정이다. 기존 6~8주 추정에 개인 AI 기억·성장·탐색 관리와 시안 기반 공통 UI 범위가 추가되었다. 사람 수만으로 선형 단축되는 일정은 아니며, 1단계에서 실제 의존성과 작업량을 확인해 다시 산정한다.

| 단계 | 기간 가정 | 주요 산출물 | 다음 단계 진입 기준 |
| --- | --- | --- | --- |
| 1. 화면·데이터 기반 | 1주 | 디자인 토큰·큐 자산 규격·5탭·9화면 연결 시제품·상태/권한/API 설계 | 시안 비교 가능, 대표 행동과 뒤로가기가 연결됨 |
| 2. 등록·탐색·상세 | 1~2주 | DB migration, 제공/희망 등록, AI 초안+수동 편집, 검색·관심·Experience | 새 사용자 두 명이 각자의 항목을 공개하고 찾을 수 있음 |
| 3. 교환 전 과정 | 2주 | 제안·버전 동의·채팅 카드·예약·이행·취소·신고·관리자 최소 기능 | 수동 검색부터 실제 두 계정의 완료까지 동시성·권한 검증 통과 |
| 4. 개인 AI·자동 탐색 | 2주 | 기억/동의/삭제, 성장 외형, 피드백 추천, 실제 탐색 작업과 알림 | 학습 허용 범위 준수, 기억 변경 반영, 실제 후보·작업 상태 표시 |
| 5. 통합 검증·초대 운영 | 2~3주 | PWA·실사용 통화/알림 검증, 운영 정책·공급 확보, 제한된 배포·파일럿 | 핵심 흐름과 복구 검증, 실제 완료·재교환·실패 원인 수집 |

디자인 자산과 공급자 콘텐츠 준비는 기능 개발과 병행할 수 있다. 단계 1의 연결 시제품은 검토용 데이터라는 표시를 두고 운영 배포물과 분리한다. 화면을 먼저 검토하되 실제 첫 출시 판정은 2~5단계의 데이터·권한·이행 완료를 기준으로 한다.

**11. 출시 검증과 운영 조건**

기능 검증:
- 제공자/수령자 방향이 로그인한 당사자에 따라 정확하게 표시된다.
- 상품 1개 또는 같은 강사의 같은 시간이 중복 예약되지 않는다.
- 제안 수정·수락 경쟁, 네트워크 재전송, 종료된 상품을 안전하게 처리한다.
- 다른 사용자가 상품 초안·주소·증빙·기억·제안 변경에 접근하지 못한다.
- 한쪽 이행·부분 이행·노쇼·분쟁을 구분하고 양쪽 확인 없이 전체 완료하지 않는다.
- 학습 미동의·동의 철회·기억 삭제·만료 일정이 추천과 파생 데이터에 반영된다.
- 상품·대화의 지시문이 AI의 권한이나 기억 정책을 바꾸지 못한다.
- 큐의 새 추천·완료 배지·탐색 상태가 실제 DB 이벤트와 일치한다.
- 빈 후보·AI 장애·오프라인·재접속에서도 수동 등록·제안·채팅 경로가 유지된다.

UI·환경 검증:
- 320/360/390/430px 및 큰 화면에서 겹침·잘림 없이 사용 가능.
- 한글 줄바꿈·텍스트 확대·키보드·하단 안전 영역·PWA 새 버전 캐시 확인.
- 두 실제 테스트 계정으로 로그인→등록→제안→협상→완료를 검증.
- 실제 두 사용자 음성/영상 통화와 알림 수신자·깊은 링크·로그아웃 후 차단을 확인.
- 시안의 세 보드와 구현 화면을 비교하여 메뉴·핵심 행동·타이포·큐 외형을 검토.

코드에 변경이 생긴 단계에서 관련 typecheck, OpenAPI 계약 검사, 교환 도메인/API 테스트, 기존 메신저 reliability와 PWA 캐시 테스트를 실행한다. 실제 DB의 동시성·권한 테스트를 별도로 포함한다. 실제 MVP 검증 결과와 아직 수행하지 않은 실기기·파일럿 검증은 릴리스 기록에 구분한다.

배포:
- DavaQ DB 백업과 복구 확인 후 전진 migration.
- DavaQ 소스·API 이미지·PWA 산출물을 독립 버전으로 배포.
- 공용 Caddy에서 DavaQ 경로가 다른 서비스 배포에 의해 사라지지 않도록 점검.
- 같은 서버의 메모리·매칭 작업·API 비용 한도 확인.
- 배포 전후 AnotherMe/DavaQ health와 도메인 경계를 확인.
- 장애 시 DavaQ 기능 플래그·이전 앱 이미지로 복구하며 이미 적용한 데이터 변경은 검토한 복구 절차를 따른다.
- 실제 공급자 확인·이용 조건·신고 대응 준비가 끝난 항목만 공개.

**12. 개발 완료의 판단 기준**

첫 가입자가 시안과 같은 화면에서 제공·희망 항목을 등록하고, 실제 후보를 찾아 상대와 합의한 뒤 양쪽 제공을 완료할 수 있어야 한다. 이후 내 큐가 확인된 피드백을 기억하고, 그 근거로 다음 후보를 다르게 추천하는 것까지 확인한다.

측정은 첫 등록 완료율, 첫 교환 완료까지 시간, 제안 수락률, 관찰 기간이 지난 교환의 완료/취소/분쟁률, 반복 교환, 기억 확인·수정·삭제 반영, 완료 교환당 AI 비용과 운영 시간을 중심으로 한다. 가짜 활동 수나 단순 접속 시간으로 성장·서비스 성공을 판정하지 않는다.

착수할 첫 작업 묶음은 “DavaQ 디자인 토큰·강제 다크 해제·5탭·공통 교환 카드·큐 자산 규격·9화면 연결 시제품·교환 상태/API 계약”이다. 다음 작업은 등록·탐색에 실제 데이터를 연결하는 것이다.
